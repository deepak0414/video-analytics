## Findings

**1. major — `src/va/pipeline/reprocess.py:352` — zero decoded frames silently wipes all Role 5/6 rows and restamps the roles clean.** `reindex_visual` (lines 151–158, same file) explicitly refuses this exact input — "truncated/corrupt media that opens but iterates nothing" — because replacing good rows with an empty rebuild while `va stale` reads clean is silent data destruction. `_reprocess_object_detector` has no such guard: `sample_frames` yielding nothing produces `frames_dets == []`, both trackers happily return empty results on empty input (verified in `iou_inproc.py`), `replace_detections`/`replace_tracks` then **delete** every existing row, the appearance shard is dropped, and the executor restamps both roles current with row_count 0. Concrete failure: a video whose media file got truncated on disk after ingest; `va reprocess --all-stale` in the same batch *fails* its visual_embedder re-embed (shard preserved, role stays stale) but *destroys* its detections and tracks and marks Roles 5/6 clean — `va objects`/`va count` silently answer "nothing" forever. Safe path: count frames in the sampling loop and raise before the writes when zero (mirroring `reindex_visual`'s check and message), so the role stays stale and the prior rows survive.

**2. minor — `src/va/pipeline/reprocess.py:379` — no removed-during-reprocess guard before the writes, unlike every sibling reprocessor.** `reindex_visual` re-checks the catalog right before its swap ("a concurrent `va remove` during the (long) re-embed... swapping now would resurrect the removed video"), and the captioner/text reprocessors fail via `backfill_text_index` returning None. The detector reprocessor loads the video once up front, then runs a potentially long real-model re-detect; a `va remove` completing mid-run is followed by `replace_detections`/`replace_tracks` re-inserting rows and the executor restamping provenance for a video that no longer exists — orphan `object_detections`/`object_tracks`/`role_provenance` rows nothing ever cleans (and `existing_classes()`-style global queries can still see the phantom classes). Safe path: re-check `Catalog.get(video.id)` immediately before the two `replace_*` calls and raise if gone, matching `reindex_visual`'s pattern.

Not findings, for the record: the two-commit range touches `src/va/adapters/`, `src/va/pipeline/`, and real-backend behavior — the critical-paths CI gate will require the `golden-verified` attestation on the PR, which is the mechanism working as designed; and the COORDINATION "same replace-window shape" claim for the web agent is slightly optimistic (two sequential commits, not an atomic swap), but no current query path joins detections to tracks across that window, so there is no concrete failure today.
