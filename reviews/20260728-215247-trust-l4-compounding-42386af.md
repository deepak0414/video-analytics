## Review findings

**1. major — `.claude/hooks/bash_guard.py:325` — only the first `until`/`while` in the command is examined, and the condition scan stops at the first `do`, so a self-observing loop that follows an earlier loop (sequentially or nested) is never checked.**
Verified allowed by the hook, and both hang exactly like the watchers that motivated the guard:
- `until [ -f /tmp/ready ]; do sleep 1; done; until ! pgrep -f portscan.py; do sleep 5; done` — "wait for A, then wait for B to exit" is an ordinary agent shape, not evasion; `_loop_at = next(...)` lands on the first loop, `_cond` collection breaks at its `do`, and the second loop's matcher is never inspected.
- `while true; do until ! pgrep -f portscan.py; do sleep 5; done; break; done` — the inner loop's self-observing *condition* is treated as outer-loop *body*.

This is the same residual class as round 1's major (a positional gap letting the exact target hazard through while plan rows 106/108 read as "this class is blocked"), and `test_trust_guards.py` covers only single-loop spellings, so the suite stays green over it. The fix direction: check every `until`/`while` occurrence, not just the first.

**2. minor — `.claude/hooks/bash_guard.py:291` — `-e`/`--regexp` is listed in `GREP_VALUE_FLAGS`, so the flag that *carries the pattern* has its value skipped as noise and the guard extracts nothing.**
Verified allowed: `until ! ps -eo args | grep -q -e portscan.py; do sleep 5; done` — `_matcher_pattern` skips `-q` as a flag, skips `portscan.py` as the `-e` value, returns `""`, and the loop hangs. `grep -e` is the standard spelling when a pattern could start with `-`. The value-skip machinery is right for `-A`/`-m`/etc., but `-e`'s value should be *returned* as the pattern, not discarded.

**3. minor — `.claude/hooks/bash_guard.py:302` — `pgrep --full` (the long form of `-f`) is not recognized, so the guard concludes the matcher "cannot self-match" and allows it.**
Verified allowed: `until ! pgrep --full portscan.py; do sleep 5; done` — hangs identically to the `-f` spelling that is blocked.

**4. minor — `.claude/hooks/bash_guard.py:350` — shell-variable patterns are false-blocked with an unusable suggestion: `pgrep -f "$PAT"` cannot self-observe (the loop's own command line contains the literal text `$PAT`, while pgrep searches for the *expanded* value), yet the guard blocks it.**
Verified blocked: `until ! pgrep -f "$PAT"; do sleep 5; done` → "pattern '$PAT' … Use the bracket trick — '[$]PAT'" — and applying that suggestion would also stop the variable expanding, so like round 1's `-u root` case it is a dead-end block. Per this branch's own new lesson, an over-broad guard is a defect too. A token beginning with `$` (or containing `${`) can't be a literal self-match and should pass.

**5. minor — `tests/test_lessons_section.py:43` — the "one-liner" length check can never fire on the file as actually authored: `entries()` captures only the dated *first physical line* of each lesson, and CLAUDE.md wraps at ~90 columns, so a lesson of any length passes the `len(ln) < 400` assertion (every current lesson already spans 2–4 physical lines).**
By this branch's own recorded lesson, a test that cannot fail against the condition it polices is decoration. Measuring the full logical entry (first line plus its indented continuations) would make it real.
