## Full review

Review complete. I verified my suspicions empirically by feeding commands through the hook itself (probe output above). The `/lesson` command, Lessons section, and `test_lessons_section.py` are sound and satisfy WT.8's "Done when"; the defects are all in the new self-observing-loop guard in `bash_guard.py`.

**Findings**

1. **major — `.claude/hooks/bash_guard.py:282`** — The guard checks only the *first* segment's first token (`_all[0][0]`), so any compound prefix skips it entirely. Verified: `cd /tmp && until ! pgrep -f portscan.py; do sleep 5; done` and `echo waiting; until ! pgrep -f portscan.py; ...` are both **allowed**, and both hang exactly like the two watchers that motivated the guard. A `cd`-prefixed command is one of the most common shapes an agent emits, so the guard misses its target hazard in ordinary (non-evasive) use. The file's own per-segment architecture already solves this: keying on *each segment's* first token would catch the prefixed forms while still excluding prose (a quoted heredoc string is one token, never a segment head). The plan's verification table row 106 claims this class is "blocked", and `test_trust_guards.py` only exercises the loop-first spelling, so the suite stays green over the gap.

2. **major — `.claude/hooks/bash_guard.py:286`** — Pattern extraction uses a regex over flattened text (`\bpgrep\b((?:\s+-\S+)*)\s+(\S+)`), which captures the *value* of a value-taking flag as the "pattern". Verified: `until ! pgrep -u deepak -f "[p]ortscan.py"; do sleep 5; done` — which already uses the bracket trick correctly — is blocked with the nonsense diagnosis that pattern `'deepak'` self-matches, and the suggested fix (`[d]eepak`) would break pgrep (not a valid user). Likewise `while ps -eo args | grep -A 2 myproc; ...` is blocked as pattern `'2'`. This is a dead-end false block, and it re-introduces the exact bug class the file's own DESIGN header ("decisions are made by TOKENIZING… never by matching flag positions… every regex attempt leaked") and the round-12 VALUE_FLAGS lesson document — the tokens are already available in `_all`; the flags should be parsed, not regexed.

3. **minor — `.claude/hooks/bash_guard.py:293`** — The guard doesn't check that the matcher can actually see its own command line, so it false-blocks loops that terminate fine: `pgrep` *without* `-f` matches process names (comm), not command lines, so `until ! pgrep -x ffmpeg; do sleep 5; done` (waiting for an encode — plausible in this repo) self-terminates yet is blocked; similarly `while [ -f /tmp/keep ]; do pgrep -f worker.py > pids.txt; ...` terminates via the file test but is blocked with the false claim "can never terminate". The bracket workaround keeps working, so this is friction rather than a dead end — but per this branch's own new lesson, "an over-broad guard is a defect too."

4. **minor — `.claude/hooks/bash_guard.py:327`** — The "2b. Self-observing polling loops" comment sits inside the per-segment loop describing a check that does not exist there (the real check is module-level and first-segment-only). It documents exactly the per-segment coverage that finding 1 shows is missing, so a future maintainer auditing the loop would wrongly conclude compound commands are covered. Same dead block duplicated into `workflow-trust-plan.md:728`.

No contract breaks (no shared-interface changes; COORDINATION.md untouched territory), no test deletions or weakenings, and CLAUDE.md/plan additions are consistent with each other — except that plan row 106's "blocked" claim overstates coverage per finding 1.
