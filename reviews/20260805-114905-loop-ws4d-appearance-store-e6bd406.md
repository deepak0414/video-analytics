**Finding 1 (major) — the crop join breaks silently under the bytetrack backend, the exact combination this feature exists for.** `_crop_key` (`ingest.py:77`) joins harvest-time crops to Role-6 output by float equality of `(round(ts,3), round(bbox,5)×4)`, on the stated invariant that trackers "never move a box" (`ingest.py:79`, `ingest.py:482`, repeated in COORDINATION.md). That's true of the stub iou tracker (`model_copy`) — which is all the tests run — but false for `bytetrack_inproc.py:45-66`: it rebuilds every detection's geometry through a float64 → float32 (×1000 nominal-pixel array) → float64 (÷1000) round-trip plus independent `[0,1]` clamps. On installed supervision 0.28 the returned `xyxy` is the adapter's own float32 array, so each coordinate carries ~3–6e-8 of quantization error — enough to flip a `round(·, 5)` boundary on a few percent of boxes — and yolo-world boxes are unclamped above 1.0 (`yolo_world_inproc.py:54-55`), so edge/near-full-frame objects can get clamped into a guaranteed mismatch. A missed key is `crop is None → continue`: the track silently gets a NULL `appearance_ref` with no warn. And the pin `supervision<0.30` has no floor and a 0.30 migration is already planned (pyproject comment); supervision versions that return Kalman track boxes make the miss total, still silent, still green in CI. Safe path: make the join positional instead of geometric — carry a harvest index through the tracker (e.g. `sv.Detections(data={"idx": ...})`, which supervision propagates through filtering) and have the bytetrack adapter `model_copy` the *original* detection like the iou adapter does, so the key is exact by construction (this also stores honest raw-detector boxes in `object_detections`); add a test of the adapter's geometry-pass-through invariant so the 0.30 migration can't re-break it; correct the false invariant comments in `ingest.py` and the COORDINATION.md entry.

**Finding 2 (minor) — unbounded crop memory.** `det_crops` (`ingest.py:484`, filled at `:512`) holds one uncompressed PIL crop per detection for the *entire* video until Role 6 finishes. An hour-long 480p ingest at 1 fps with yolo-world (~10 detections/frame, large crops for close objects) accumulates tens of thousands of crops — on the order of 1–2 GB — alongside the resident real models, on the same box WS4.e already flags for OOM. Safe path: bound it — spill crops to the transient `cache/` dir, or defer cropping to a targeted seek-decode of only the winning frames after tracking.

**Finding 3 (minor, carried forward, still unaddressed in this range)** — the NVR identity (`nvr.py:152` `source_key nvr:ch<n>:<epochs>`, camera id `nvr-ch<n>`) omits any recorder identifier while `VA_NVR_HOST` selects the recorder at fetch time; repointing the env at a second recorder dedups to the first recorder's footage and collapses both channel-N cameras into one row. Same safe path as the prior review: fold a recorder id into the identity now, or document the single-recorder assumption.

Checked and dismissed: appearance-shard append-on-retry (mirrors the pre-existing frame-store pattern, shard unsearched, reingest cleans it); appearance failure not marking the role stale (NULL ref is a documented state and the step is an explicit best-effort sub-step of Role 6); same-frame key collisions (identical pixels at 5-decimal resolution); crop-skip of zero-area boxes (degenerate anyway). No disputes in workflow-trust-plan.md touch these findings.
