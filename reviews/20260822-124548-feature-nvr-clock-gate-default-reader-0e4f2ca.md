### 1. CRITICAL — real RapidOCR output false-rejects GOOD footage; the "fail open" guarantee does not hold on real frames
`src/va/sources/ocr_clock.py:78` — `_CLOCK_RE` accepts a **1-digit day/month/hour** (`\d{1,2}`). I checked the reader against ground truth that exists locally: the 9 806 real RapidOCR rows in `.va-24h/catalog.db` (real Lorex frames, correct `start_epoch`, median skew 1 s). RapidOCR **systematically drops the leading "1" of the day field** (`08-1-2026 10:55:58AM` for 08-**11**-2026), and it does so *consistently within a clip* because the overlay pixels barely change frame to frame: 55 body rows (t ≥ 1 s) across 21 correctly-delivered videos parse exactly −864 000 s (10 days) off, and **4 videos have a strict MAJORITY of their parsed reads off** (`12cf4c36` 5/5, `7dbbd995` 7/9, `af8e0846` 3/3, `68cbcd18` 1/1). The 8 head frames span 0.4 s with near-identical overlays, so "cross-frame consensus" supplies almost no independence — the exact "confident, large, consistent" signal the gate is built to act on. Result: `verify_delivery` rejects, `_pull_window` retries MAX_TRIES, the exact-window fallback re-OCRs the same pixels and rejects again, the window is "unpullable", and `watch.py:222-237` holds the camera's watermark and aborts its pass — a ~1–2 %-of-pulls false reject that **stalls a camera** until the window rolls off the ring. CLAUDE.md:119 now states "never a false-reject of good footage on OCR noise"; this data contradicts it.
**Safe path (data-backed):** the Lorex overlay is zero-padded `MM-DD-YYYY hh:mm:ss` (every correct real row confirms it) — require `\d{2}` for month/day/hour so a dropped digit is a NON-parse (fail open). Against the same 9 806 rows: parse count 7 310 → 7 224 (−1 %), off rows 55 → 2, majority-off videos 4 → 1 (and that one has a single parsed row, below `MIN_AGREE_FRAMES`). Also validate the shipped reader against the real `.va-24h` frames/rows (they are on disk; the opt-in `RUN_OCR_CLOCK` test renders PIL's default ~11 px bitmap font, which is not the real overlay) and report the comparison per the "determinism is not correctness" rule — COORDINATION.md already admits "validated on synthetic clocks only".

### 2. MAJOR — a recoverable cross-camera head of ≥5 frames now REJECTS instead of trimming
`src/va/sources/ocr_clock.py:172-183` + `src/va/sources/verify.py:186-197`. The consensus drops the **aligned minority** and emits only the largest cluster. For a stale cross-camera lead-in (which carries its own ~7-day-old clock — the census says so explicitly) of 5–8 of the 8 inspected frames, the consensus is the STALE frames, every emitted reading is foreign, there is no aligned tail → `_head_trim` returns **reject**, and `verify_delivery` returns it before the dHash trim is applied. I reproduced it with the pure functions at 20 fps: 3/4 stale frames → trim (0.15/0.20 s) with or without the reader; **5/6 stale frames → trim without the reader, REJECT with it**. The census head band is 1–5 frames, so 5 is in-distribution; CLAUDE.md:128 still claims "cross-camera heads are trimmed", now false for that case, and the regression is untested (no test combines a dHash-foreign head with clock readings).
**Safe path:** emit every cluster with ≥ `min_agree` members (drop only singletons as noise) so the verifier's existing prefix logic can trim at the aligned tail, or run the clock gate over the post-dHash-trim frames; add a test for "5 stale + 3 aligned head frames → trim, not reject".
