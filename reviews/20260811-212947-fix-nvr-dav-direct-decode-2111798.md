## Full review

Review complete. The commit is a focused, well-reasoned fix — it removes the `-c copy` mpegts remux (which was falsely rejecting good `.dav` pulls) and reads the `.dav` directly with `+genpts` in both downstream consumers. The two ffmpeg consumers (`_frame_hashes`, `_trim_encode`) use identical `-fflags +genpts` input flags, so the sampling clock and the trim clock stay consistent; the docstrings carry live ground-truth measurements (47 MB reproduction case, 28.00 s trim accuracy), which satisfies the determinism-is-not-correctness rule. Test renames (`window.ts` → `window.dav`) are mechanical and weaken nothing; the external contract (cached mp4, source_key, schema) is unchanged, so no COORDINATION.md entry is required. No new env vars, flags, or config keys, so no documentation-parity gap. The commit subject is a provisional `need_agent_review:`, exempt from the clarity rule.

Two minor findings, both in the retry loop's validity handling:

**1. minor — `src/va/sources/nvr.py:529` — the retry loop lost its only payload-validity gate.** Previously a downloaded `.dav` also had to survive the remux before being accepted; failures consumed retry attempts. Now any body over 2000 bytes returns on attempt 1, and a large-but-undecodable payload (transient device garbage, or an oversized CGI error body) skips the remaining `MAX_TRIES − 1` retries and hard-fails the whole pull downstream at the "only N decodable frames — nothing to verify" check. In the watcher this holds the watermark and burns a device pull per cycle until it happens to succeed; a manual `va ingest nvr://…` just fails once. Safe path: keep the fix (no remux), but run the cheap decodability check (e.g. the `< 3` decodable-frames test via `_frame_hashes`) inside the retry loop so a transient bad payload still consumes retries, leaving the downstream raise as the final backstop.

**2. minor — `src/va/sources/nvr.py:527` — a curl timeout still truncates silently despite the "Sized, not guessed" comment.** `_curl` runs with `check=False` and never inspects the exit code. The comment itself records that the device "degrades under session pressure"; if a transfer exceeds 180 s, curl exits 28 leaving a partial `.dav` over 2000 bytes, which line 529 accepts as a successful fetch. Truncation cuts the tail cleanly, so the self-consistency check sees a shorter-but-consistent clip and the "trimmed" warning never fires — the window ingests silently short, which in security footage means missing moments with no operator signal. This blindness predates the commit (the old 60 s ceiling had it worse), but the commit re-sized the timeout on the theory that it now fits — detection would make that theory safe. Safe path: return `subprocess.run(...).returncode` from `_curl` and treat a nonzero exit (especially 28) in `_fetch_window` as a failed attempt to retry, not a success.

No critical or major findings, so the verdict is approve.
