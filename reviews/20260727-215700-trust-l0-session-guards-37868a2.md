I do not repeat them. However, empirical probing found two new gaps of the same "invariant vs. literal spelling" class, one level deeper.

**1. (major) `.claude/hooks/stop_gate.sh:16` — the cache key ignores untracked-file *content*, so a stale green blesses a red suite.** `git diff HEAD` excludes untracked files and `git status --porcelain` contributes only the `?? path` line, which is constant across edits. Reproduced end-to-end in a scratch repo: create untracked `src/untracked.py` (suite green) → gate caches green → rewrite that untracked file so the suite is red → gate exits 0 without running pytest, while pytest actually exits 1. This is the routine state of active development (this very worktree has untracked `src/va/adapters/reasoner/qwen3vl_inproc.py` and `tests/test_migrations.py`), and it's the remaining variant of the HEAD-omission staleness the previous review flagged as major. The key needs untracked content (e.g. hash the files `git status` lists as `??`, or `git add -N` before diffing).

**2. (major) `.claude/hooks/bash_guard.py:70` — the force-push rule misses git-native force spellings.** Verified against the guard: `git push origin +main`, `git push origin +HEAD:main` (the `+refspec` force syntax), and bare `git push --force` / `git push -f` (which force-push the current branch's upstream — i.e. main, from a main checkout, with no "main" token in the command) all return **allow**; only the `--force`/`-f` + literal `main` spellings block. These are documented git equivalents of the exact command the rule names, not shell obfuscation, so they fall under the file's own "rules target INVARIANTS, not literal spellings" standard — the same standard by which the reorder variant was judged major last round. And there is no layer behind it: `.githooks/pre-push` has no force-push detection (its gates check content/review state, not history rewrite), and `.github/`/branch protection (WT.5) doesn't exist yet.

**3. (minor) `.claude/hooks/bash_guard.py:46` — the block message promises an override the script doesn't implement.** The machinery-write message says "`touch .guard-override` opens a maintenance session," but bash_guard never checks that sentinel (only path_guard does; bash_guard doesn't even import `os`). In a sanctioned maintenance session, Bash operations on machinery — e.g. `chmod +x` on a newly Written hook — stay blocked and the agent is misdirected by the guard's own remedy text.

**4. (minor) `tests/test_trust_guards.py:314` — the variant tables still stop one level short of the invariants.** Neither `+refspec`/bare-force pushes nor untracked-content staleness appears in the blocked tables/stop-gate tests, so both majors above pass the 85-test suite green — the same "tables mirror the regexes" root cause the previous round named, recurring on the residue.
