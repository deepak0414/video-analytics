## Review — `trust/l0-session-guards` (origin/main..HEAD)

I re-checked the four findings in the newest ledger (`reviews/20260727-215700-…-37868a2.md`) against the current tree: all four are genuinely fixed (untracked-content hashing in the cache key, `+refspec`/bare-force detection, `.guard-override` honored by bash_guard, expanded test tables). I don't repeat them. Two new gaps of the same "invariant vs. spelling" class survive, both reproduced by running the shipped scripts.

**1. (major) `.claude/hooks/stop_gate.sh:17` — the cache key excludes the hook/script files the suite actually tests, so a stale green blesses a red suite.** The key covers `src`, `tests`, and `pyproject.toml` only, but `tests/test_trust_guards.py` drives the real `.claude/hooks/*` scripts and `tests/test_trust_hooks.py` drives the real `.githooks/*` and `scripts/*` scripts. Editing any of those — the entire content of trust-layer work, including this branch — leaves the cached green valid. Reproduced in a scratch repo: green run caches; then break `.claude/hooks/guard.py` and make pytest exit 1 → the gate exits **0 without running pytest**; the control (same red suite, edit under `src/`) correctly exits 2. This is validation-matrix row 12 failing for the one work area the branch introduces, and the third instance of the staleness class the previous two rounds each flagged as major.

**2. (major) `.claude/hooks/bash_guard.py:80-99` — force-push to main is still allowed via an explicit `HEAD` refspec.** The rule blocks when a literal `main`/`master` appears, or when there is no refspec at all (`nonflags <= 1`, resolving the checked-out branch). An explicit non-`main` refspec that still targets main falls between the two. Verified against the shipped guard from a `main` checkout: `git push --force origin HEAD` → **allow (rc 0)**, `git push -f origin @` → **allow (rc 0)**, while `git push --force` → block and `git push --force origin HEAD:refs/heads/main` → block. `HEAD` is an everyday spelling, not obfuscation, so it sits inside the file's own "rules target INVARIANTS, not literal spellings" standard. Nothing is behind it: `.githooks/pre-push` has no force-push detection and `.github/` (WT.5) does not exist. The fix is to treat a refspec whose source is `HEAD`/`@`/the current branch as a force of the upstream and run the same branch resolution.

**3. (minor) `tests/test_trust_guards.py:356-360, 607` — the tables again mirror the regexes rather than the invariants.** `BLOCKED_COMMANDS` has `+main` and `+HEAD:main` but no `--force origin HEAD`/`-f origin @`; the stop-gate tests cover untracked `src/` content but no hook/script edit. Both majors above therefore pass the suite green — the same root cause the plan names at `workflow-trust-plan.md:709-717`, one level deeper.

**4. (minor) `.claude/settings.json:5` — the deny rule is broader than the guard and contradicts the test's own allow-list.** `Bash(git push --force*)` is a prefix match, so it also denies `git push --force-with-lease origin <feature>` — which `ALLOWED_COMMANDS` (line 408) explicitly asserts is permitted and which bash_guard does permit. The deny list wins at the permission layer, so force-with-lease on a feature branch (needed after any rebase onto main) is unusable, and the passing test misrepresents the effective policy. Narrowing to `Bash(git push --force origin main*)` or dropping the redundant rule in favor of the guard resolves it.

**5. (minor) `.claude/hooks/bash_guard.py:36-37` vs `CLAUDE.md:124-126` — the override's full-exemption semantics are broader than the docs state.** `.guard-override` returns before every rule, so during a maintenance window `touch .commit-approved`, `AGENT_REVIEW=skip`, `gh pr merge`, and `reviews/` writes are all permitted. The plan records this as a deliberate choice (`workflow-trust-plan.md:715-717`, "full-exemption semantics, matching path_guard"), so I'm not disputing the design — but CLAUDE.md's new paragraph describes the override only as opening "gate maintenance" while still calling the sentinel unconditionally human-only ("NEVER create it yourself"). One clause noting that the override suspends all guards would close the gap.

Verified and dropped: `-[a-zA-Z]*n` has no false positive on `--amend`/`--no-edit`; `path_guard`'s `normpath` closes `../` traversal and correctly allows absolute paths outside the root; the `reviews/` and machinery rules don't block the documented `git add reviews/` or read-only inspection; the `agent-review.sh` 480→900 s bump is consistent with the background-push guidance already recorded in the plan; no existing test was deleted or weakened; the COORDINATION.md entry satisfies the shared-interface logging rule. I could not run pytest directly (sandbox denied), so findings 1-2 come from executing the guard scripts themselves with PreToolUse-shaped payloads.
