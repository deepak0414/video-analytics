## Findings

**1. major — `scripts/review_scope_hash.sh:11` (with `.githooks/pre-push:31-37`): any non-doc file placed under `reviews/` ships unreviewed by riding an existing approval.** The approval hash excludes `reviews/` entirely, but nothing restricts that directory to `.md` ledgers (pre-commit's gates only require staged `.py` to *compile*, and commit-msg's docs-only classification also excludes `reviews/` wholesale). Scenario: a branch is reviewed, approved, and finalized (`.git/.review-approved` holds the matching hash — the normal end state of every lifecycle). The agent then adds `reviews/evil.py` (or any code file) and commits it as `wip: ledger tidy` — free at commit-msg. At push, Gate 2's trigger sees a non-md file and enters the review path, but `cur` (which excludes `reviews/`) still equals the stored approval, so it prints "skipping re-review" and the never-reviewed file reaches origin. Gate 3 passes (no provisional subject). This directly falsifies the CLAUDE.md/plan claim that unapproved content "can never reach main unreviewed." Fix direction: narrow the exclusion to `reviews/*.md` (in both the hash and commit-msg), or add a pre-commit gate that `reviews/` may contain only `.md` files.

**2. major — `.githooks/pre-push:32`: the approval hash is always computed from `HEAD`, but Gate 2 runs per pushed ref, so pushing a non-checked-out ref compares the wrong content.** `review_scope_hash.sh` hashes `git diff origin/main HEAD`, while the loop's `$local_sha` may be any ref (`git push origin other-branch`, `git push origin sha:refs/heads/x`, multi-ref pushes). Two failure directions: (a) *skip*: with an approved `feature/x` checked out, pushing `feature/y` (= `feature/x` plus an unreviewed `wip:` commit) computes `cur` from `feature/x`'s diff, matches the stored approval, prints "skipping re-review", and the unreviewed commit ships; (b) *bless*: after a backstop review of a pushed non-HEAD ref approves, line 37 writes `cur` — the hash of the *checked-out, never-reviewed* branch — into `.git/.review-approved`, pre-authorizing a later push of that content. The hash must be computed from `$local_sha` (e.g. `git diff origin/main "$local_sha" -- . ':(exclude)reviews'`), with per-ref approval records. The sandbox tests only ever push the checked-out branch, so this path has zero coverage.

**3. minor — `.githooks/commit-msg:27`: the docs-only test fails open when `origin/main` is absent.** `git diff --name-only origin/main … 2>/dev/null` produces empty output on a clone without the baseline ref, so tracked code changes vanish from the classification and a plain-subject commit of code is accepted as "docs-only." post-commit (line 15) and pre-push (line 20) both explicitly fail closed on the same missing ref — commit-msg is the one gate in this diff still silently degrading. Contained (the push gates still block later), but inconsistent with the fail-closed posture this PR's own as-built notes claim was applied.

**4. minor — `workflow-trust-plan.md:567-579` (also 525-553): the plan's "verbatim intended implementation" block for `review_scope_hash.sh` still shows the worktree-scoped hash (diff of worktree + sha256 of untracked files) that this PR's headline fix removed.** The diff edited that very block (adding the `reviews/` exclusion) while leaving the worktree scope, so it now contradicts both the shipped script and the design bullet at lines 492-499 in the same document; the embedded post-commit block is similarly stale (no fail-closed `origin/main` check). The plan states "File contents given here are the intended implementation, verbatim" — a future agent implementing from the doc would resurrect the exact bug matrix row 29 regression-tests against.
