I verified the fix's premise against the code (`registry.get_object_detector` does build a fresh adapter per call at `src/va/registry.py:198-214` while `MANAGER.get` caches one model), that the marker is only set after a successful `set_classes` (no false-primed state), that ingest's best-effort guard around `detector.detect` matches the described failure mode (`ingest.py:571-592` at HEAD), and that the regression test would genuinely fail on the pre-fix code (fresh `det2` with per-instance `self._classes = ()` calls the fake's raising `set_classes`). The test needs no GPU/network (MANAGER is monkeypatched; `resolve_device("cpu")` short-circuits before importing torch). A pytest run was live in another session and my single-file run was declined, so verification is by inspection.

Two minor findings, neither blocking:

**1. minor — `src/va/adapters/object_detector/yolo_world_inproc.py:45` — the acknowledged vocab-change caveat is reachable through supported commands, and the in-code claim "one vocab per workdir/profile" is not actually enforced anywhere.** Footage profiles set `classes:` per video (`va ingest --profile`, `videos.profile`), so one long-lived process — the `va serve` durable job queue, or a reprocess/watch pass over mixed-profile videos — can legally present two vocabularies to the same cached model. The second vocabulary re-primes and hits the same CPU/CUDA mismatch, and Roles 5+6 are silently best-effort-skipped for every video of the second profile: exactly the class of silent gap this fix was written to close, now confined to a combination (real yolo-world backend × mixed profiles × one process) nobody tests. The fix is strictly narrower than the pre-fix bug and the caveat is flagged in-code, hence minor — but the safe path is to make re-prime survivable rather than rare: on `set_classes` failure, evict and rebuild the model through `ModelManager` (or move the class-text tensors to `self.device` before priming), and cover the two-vocab path with a test.

**2. minor — `tests/test_yolo_world_reprime.py:62` — no test asserts that a *changed* vocabulary still re-primes, so the guard's comparison half is uncovered.** A wrong implementation that marks the model with a boolean (never re-priming for any vocab, e.g. `if not getattr(model, "_va_primed", False)`) passes both new tests while silently detecting with the wrong class list forever after the first prime — wrong results, not a crash, so nothing downstream would flag it. Add a third case: prime with `["car"]`, then detect with `["boat"]` on a fake whose `set_classes` doesn't raise, and assert a second call arrives with the new classes.

Everything else checked out: no contract/schema changes, no new env vars/flags/config keys needing docs, no test deletions or weakenings, best-effort semantics preserved, the commit subject is a provisional `need_agent_review:` (exempt from the finalized-message rule), and the determinism claim in the comments is backed by a named ground-truth incident (the .va-24h 231-window gap) rather than asserted.
