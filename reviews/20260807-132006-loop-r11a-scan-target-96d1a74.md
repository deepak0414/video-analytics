## Findings

**1. major — the newly-routine derived target `"the color"` canonicalizes to the shared `"default"` cache bucket, so a later ask on the same video silently serves the earlier sweep's observations as its own CODE-COUNTED answer.**

`derive_scan_target` now emits `"the color"` for the archetypal counting query (`rule_inproc.py:75`; on `origin/main` that query derived `None` → `DEFAULT_TARGET` → bucket `"outfit"`). But `canonical_key` (`deep_scan.py:73`) strips `color`/`colour`/`wearing`/`person`/`state`/… via `_KEY_NOISE` and falls back to the literal string `"default"` when nothing survives — and `prompt_key` is built from that key alone. The change turns a previously-unoccupied collision bucket into the common case.

Verified live on a synthetic clip:

```
q1 "how many times does the color change in the video?"      -> target 'the color'   -> key default
q2 "how many times does she change what she is wearing?"     -> target 'the wearing' -> key default
first  target='the color'   cached=False frames=4
second target='the wearing' cached=True  frames=4   identical observations: True
evidence: CODE-COUNTED from an exhaustive scan of 4 frames of 'the wearing': 3 DISTINCT states...
```

With a real VLM the second sweep never runs: the user gets the color sweep's numbers, attributed to "the wearing", flagged `cached`, and `ask()` *leads the rendered answer* with them. The same bucket also swallows plausible LLM-planner targets (`"the color of the garment"`, `"the person wearing"`, `"the main person's current state"` — all → `default`). Smallest fix: make the fallback content-derived instead of a shared literal, e.g. `return "-".join(t for t in tokens if t) or "t" + hashlib.sha1(" ".join(sorted(raw)).encode()).hexdigest()[:10]` — distinct all-noise targets then get distinct buckets (worst case a cache miss, never a wrong count). Alternatively drop `color`/`colour`/`wearing` from `_KEY_NOISE`, which are now legitimately the *entire* subject. Add a pin test asserting two different all-noise targets do not share a sweep.

**2. minor — the `_SUBJECT_NOUNS` whitelist is unconditional, not the "when nothing else survives" fallback both comments describe, and it injects the counting word `number` into targets for the `"the number of X"` phrasing.**

`_SUBJECT_NOUNS ⊂ _STOP ⊂ _SCAN_NOISE`, so `w not in _SCAN_NOISE or w in _SUBJECT_NOUNS` (`rule_inproc.py:74-76`) lets those three words through *always* — contradicting `rule_inproc.py:60-63` ("ARE the subject when nothing else survives") and the docstring. Probed: `"count the number of visits"` → `'the number visits'` and `"how many times does the number of people change?"` → `'the number people'`, where `origin/main` derived `'the visits'` / `'the people'`. The repo's own `_COUNT` regex classifies `number of` as counting language, so the sweep now asks the VLM to name "the number visits". Safe path that satisfies both this and the round-4 finding it came from: keep one plain filter, and only when it empties fall back to keeping `_SUBJECT_NOUNS` members — that yields `'the color'` for the color query, `'the visits'` for the counting phrasing, and still `None` for pronoun-only queries.

**3. minor — a tracked doc still prescribes work on the deleted `DEFAULT_TARGET`.**

`qwen3vl-reasoner-experiment.md:134` carries an open "Follow-ups (not done)" item: *"change `DEFAULT_TARGET` from the outfit-specific string to a neutral `"the main subject"`"*. That symbol no longer exists, and the neutral-default idea is the opposite of what R11.a decided (no canned fallback at all). A next session picking up that follow-up greps for `DEFAULT_TARGET`, finds nothing, and may re-derive the wrong conclusion. Safe path: strike or annotate the follow-up in this change ("superseded by R11.a — targets derive from the query; no default"), since this is the change that invalidated it.

Scope notes: the "security footage can never deep-scan" policy itself is out of scope — `deep_scan: "off"` was authored into `security.yaml` on main by WS2.d; this change only consumes it, which is what R11.a's Done-when asks for. The `need_agent_review:` subject is exempt from the commit-message rule.
