This branch adds the per-camera watermark watcher (`pipeline/watch.py`, `va watch`, schema v8) plus two jobs-queue hardening fixes. It has been through five prior review rounds; I re-verified the claimed fixes independently rather than trusting the annotations, and probed the fresh surface.

**What I verified and it holds:** the deferral-before-clustering logic (round-3 critical) is correctly placed — `cluster_events` really does keep only the first event's attributes; the straddle filter (`start_epoch >= watermark`) composes with the deferred-start cap so a deferred episode is re-included next pass; `set_watermark`'s SQL is monotonic so the stale-read comparisons at `watch.py:238/246` can't rewind; the per-camera budget split, deduped-replays-are-free rule, and giant-episode progress are each pinned by an exact-window test; migration v8 agrees with the fresh-create schema and the `MIGRATIONS == SCHEMA_VERSION` assert holds; the jobs revert-to-queued and pollable-failed-ask changes both come with tests that would fail on the old code; the watcher's bare `ingest(uri)` call does get the security profile (derived inside `_ingest_impl` from the nvr source type, not in the CLI); the monkeypatched-ingest test works because `catch_up` imports `ingest` at call time; new CLI flags and the schema bump are documented in CLAUDE.md and logged in COORDINATION.md. The commit subject is a provisional `need_agent_review:` — exempt from the clarity rule (note for the finalize digest: describe the watcher in plain terms first).

**One new finding (major).** The round-5 fix for degenerate sub-second windows reintroduces the very wedge it was written to prevent, one input class over. `_window_uri` (`watch.py:77-78`) floors the start and ceils the end *independently*, so a window can widen to `MAX_WINDOW_S + 1` seconds — and `parse_nvr_uri` (`nvr.py:93-97`) hard-rejects any span over 120 s. `_episode_windows` splits at exactly 120 s from a possibly-fractional start, so **any fractional-epoch episode longer than one window** produces a first window like `(10.4, 130.4)` → URI `10 … 131` = 121 s → `ValueError` inside `ingest` → caught at `watch.py:215` as a failed window → watermark held → the *identical* URI is rebuilt and fails every pass. The camera is wedged until the log entry itself ages out, and everything behind the ring buffer's edge is lost meanwhile. (An unsplit episode with fractional ends and span > ~119 s hits it too: `ceil(end) − floor(start)` can exceed the raw span by up to 2.) Today's real adapter (lnr-eventlog) emits whole-second epochs via `strptime`, so this fires only on a fractional-epoch MotionSource — but that is exactly the source class the round-5 docstring says this function defends against, and the failure is silent permanent data loss. Safe path: clamp `hi = min(hi, lo + MAX_WINDOW_S)` in `_window_uri` — contiguity is preserved because the next split window's start is exactly `start + 120`, whose floor equals the clamped `hi`; for an unsplit tail the trim is < 1 s, within the function's own stated tolerance. Add a fractional-start-episode-over-120 s case next to `test_fractional_subsecond_event_pulls_widened_window`. (The clamp also removes the current 1 s overlap between adjacent split windows — `ceil` of one end vs `floor` of the next start duplicates a second of footage in two chunks.)

**Carried-over minor (previous round, undisputed, still present):** `va watch --interval 0` is advertised as cron-friendly but has no single-instance guard (no flock/pidfile in `watch.py`/`cli.py`), so an overlapping cron firing re-reads the same watermark and double-pulls/double-ingests concurrently — doubled NVR/GPU work and SQLite lock contention surfacing as spurious "watermark held" retries. Take a non-blocking lock on `<workdir>/watch.lock` in `catch_up` and skip the pass if held, or document that cron entries must wrap in `flock -n`.

Probed and dissolved: the quiet-advance comparison against the pre-pass watermark (SQL monotonicity makes it safe), the recovered lost-End instant merging into clusters (split handles it), all-deduped giant-episode passes (budget uncharged, episode completes), `AskQueue`'s fallback using `r["id"]` inside the except (the id column always exists; only the payload can be malformed), and camera-count > max_windows overshoot (documented in the help text).
