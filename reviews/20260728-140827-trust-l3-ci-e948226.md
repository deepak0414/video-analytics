## Review: `origin/main...e948226` (WT.5–WT.7 CI gates)

**Verdict: request_changes.** Two majors, both in the same place the last two backstop rounds have been circling — the label gate's "a human applied this" premise. The CI wiring itself (workflows, template, checker logic, plan sync) looks sound; the SIGPIPE and prefix-matching fixes from round 1 are genuinely correct now, and the round-2 `cache-dependency-path` fix addresses a real first-run failure. I did not repeat any finding the two ledgers in `reviews/` already raised and this tip commit resolved.

I verified the guard findings by running the hooks directly rather than reasoning about them. I could **not** run the pytest suite — `.venv/bin/pytest` required an approval unavailable in this session — so nothing below is a claim about test pass/fail state.

**Major 1 — the `gh api` mutating-route block only catches the separate-token flag spelling** (`.claude/hooks/bash_guard.py:364`). `mutating = any(m in gargs for m in ("PATCH", ...))` is exact-token membership, so `-XPATCH` and `--method=PATCH` never match. Measured against the shipped guard: `gh api -X PATCH repos/o/r/issues/14 --input /tmp/p.json` → exit 2 (the form the new test covers), but `gh api -XPATCH repos/o/r/issues/14 --input /tmp/p.json` → exit 0, `gh api --method=PATCH …` → exit 0, and `gh api graphql -F query=@/tmp/m.graphql` → exit 0. The `--input`/`@file` forms also defeat `mentions_label`, since the label string lives in the file, not in argv. Concretely: an agent writes `{"labels":["human-reviewed"]}` to a temp file, runs the attached-flag PATCH, and `critical-paths` goes green with nobody reading the diff. This is the round-14 lesson ("attached and short flag spellings included") recurring in the code that fixed row 85.

**Major 2 — the new gate machinery is writable by the agent, and CI runs the PR's copy of it** (`scripts/check_critical_paths.sh`, `scripts/critical_paths.txt`). Neither file is in `bash_guard.is_machinery()` (`.claude/hooks/bash_guard.py:177` lists only `agent-review.sh`, `review_scope_hash.sh`, `setup-hooks.sh`) nor in `path_guard.MAINTENANCE_PROTECTED` (`.claude/hooks/path_guard.py:40`). Measured: `sed -i s/x/y/ scripts/check_critical_paths.sh` → exit 0, `echo x > scripts/critical_paths.txt` → exit 0, Edit on both → exit 0; for comparison `scripts/agent-review.sh` and `.github/workflows/pr-gates.yml` → exit 2. Because `pr-gates.yml` runs `bash scripts/check_critical_paths.sh` from the PR checkout, one commit deleting the `scripts/`/`.github/` rows (or making the checker `exit 0`) turns the gate green in the same PR that weakens it. CLAUDE.md states the guards block edits to "trust scripts"; that is now inaccurate for the two files the gate is made of.

Three smaller things. The SIGPIPE regression test (`tests/test_trust_guards.py:597`) writes 601 paths of ~24 bytes ≈ 14 KB, which fits entirely in the 64 KB pipe buffer — the old `printf | grep -q` form would not have received SIGPIPE and would have passed this test, so it does not cover row 82 (it also adds ~1,200 git subprocesses to every CI run; ~2,600 paths would be needed to actually exceed the buffer). `git diff --name-only` at `scripts/check_critical_paths.sh:18` prints only the destination path of a rename git detects, so `git mv src/va/cli.py src/va/cli2.py` with edits touches a critical file while matching no exact-file pattern. And `mentions_label` (`bash_guard.py:347`) fires on read-only commands too — `gh pr list --label human-reviewed` → exit 2 — so an agent cannot check whether the human has labeled a PR.

One contract note: the only branch-protection recipe in the plan (`workflow-trust-plan.md:1530`) requires the `offline-tests` context alone, so red `evidence`/`critical-paths` checks are advisory, while the new COORDINATION.md entry tells the other agent these gates block merge.
