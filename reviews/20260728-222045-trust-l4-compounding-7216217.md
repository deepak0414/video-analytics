## Review: `7216217` (WT.8 — /lesson, Lessons section, self-observing-loop guard)

The `/lesson` command, Lessons section, and `test_lessons_section.py` match the WT.8 spec and its as-built notes; the lessons tests pass (7 entries, budget enforceable). The problems are all in the new loop guard in `bash_guard.py`.

**1. MAJOR — multi-line commands bypass the loop guard entirely** (`.claude/hooks/bash_guard.py:347`). `SEPARATORS` (line 346) lists `"\n"` as a valid token before a loop opener, but `_stream` is built by flattening lines *without* inserting newline tokens — so `"\n"` in `SEPARATORS` is dead code, and an opener at the start of line 2+ fails the previous-token check. Verified: `echo starting⏎until ! pgrep -f portscan.py; do sleep 5; done` is **allowed** (the same command joined with `;` is blocked). This is the guard's core blocked-case escaping in the most common command shape, it repeats the round-15 critical documented in `segments()`'s own docstring ("multi-line command collapsed… every rule keyed on the first command name skipped lines 2+"), and no test in `BLOCKED_COMMANDS` uses a multi-line loop. Caveat for the fix: the heredoc-prose case currently passes *only because of* this bug (heredoc body lines are tokenized as commands), so naively appending `"\n"` tokens will false-block heredocs quoting a loop — both cases need tests.

**2. minor — quoted multi-word patterns are re-split by whitespace, false-blocking a correctly-mitigated loop** (`bash_guard.py:359-360`). `" ".join(_cond)…split()` discards the shlex tokenization, so `until ! pgrep -f "python3 [w]orker.py"` — a valid bracket trick that cannot self-match — is judged on its first word `python3` and **blocked** (verified). The repo's own lesson says every false block pushes toward a workaround; the block message also reports the wrong pattern for genuine multi-word hits.

**3. minor — clustered/attached short-flag values defeat `_matcher_pattern`** (`bash_guard.py:328-331`). `grep -qe portscan.py` (the `-e` value IS the pattern — the exact case the code's comment claims to handle) and `grep -m1 portscan.py` (attached value; the *next* token, the pattern, is wrongly consumed) both return `""`, so those self-observing loops are **allowed** (verified). Same defect class as the round-3 `pgrep -fu` finding, one spelling over.

**4. minor — stage commands read `_st[0]` directly instead of via `command_name()`** (`bash_guard.py:362`, `366`). An env prefix disables the rule: `until ! LC_ALL=C pgrep -f portscan.py; do…` is **allowed** (verified) — violating the file's own round-13 rule ("ONE definition, used by every rule — a rule that read seg[0] directly was disabled by an env prefix").

**5. minor — `SEPARATORS` omits `else`/`elif`** (`bash_guard.py:346`), so `if …; else until ! pgrep -f job.py; do …; done; fi` bypasses the check (verified allowed).

No contract breaks (no `src/va` changes in range), no CLAUDE.md content-rule violations, no tests deleted or weakened; findings 1 and 2 are also test-coverage gaps (no multi-line or multi-word-pattern fixtures).
