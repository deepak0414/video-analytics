**Two findings, both minor:**

**1. `reingest_video` drops `start_epoch` across the remove+ingest cycle** (`src/va/pipeline/manage.py:112-148`). The branch itself established the invariant "reingesting a chunk must not sever its chunk metadata" and implemented it for `profile` and `camera_id` (including the failure path), but the very next commit adds the third piece of chunk metadata without extending the carry. Once WS-4's NVR source sets `start_epoch`, a reingest (the documented remedy for model changes *and* the remedy this branch's own stale flow prints for profile-disabled roles) silently NULLs the time base; `wallclock_to_chunks` then skips the chunk, so it vanishes from wall-clock queries with no warning. Graded minor for consistency with how the identical forward-looking camera gap was graded in the WS3.a round (nothing writes the field in production yet). Safe path: carry `existing.start_epoch` in the same reattach helper (success + failure paths), or record it as an explicit WS4.c carry-over in the loop doc alongside the FK items.

**2. The documented "open-ended `rel_end=None`" contract is dead code** (`src/va/pipeline/timeline.py:46-48` and `:64`; echoed in COORDINATION.md's WS3.b entry "unknown-duration chunks come back open-ended"). The `else None` arm can never execute: the `v.start_epoch > t1: continue` guard above guarantees `t1 >= v.start_epoch`, so an unknown-duration chunk always gets `rel_end = t1 - start_epoch` — capped at the query range, which is the behavior the test actually pins (`test_unknown_duration_chunk_is_included_open_ended` asserts `(50.0, 80.0)`, not `None`). The capped behavior is correct; the docs are wrong. A WS-4/5 caller coding to the docstring/COORDINATION contract either writes a `rel_end is None` branch that never runs or assumes coverage past t1 that the function deliberately caps. Safe path: correct the docstring, `ChunkRange` field comment, test name, and the COORDINATION.md entry to say "capped at t1", and delete the unreachable `else None`.
