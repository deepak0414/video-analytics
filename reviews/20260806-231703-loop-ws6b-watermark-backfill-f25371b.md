## Full review

The review is complete. All prior-round findings (deferred-ordering watermark leak, wedged open instants, vector duplication, poison-job cap, requeue races) were verified as fixed with covering tests. ## Findings

**1. Critical — `src/va/pipeline/watch.py:142` — clustering destroys the `open` marker, so a still-recording episode can be classified "settled" and its footage lost forever.**

`catch_up()` clusters the raw events (`episodes = cluster_events(events, gap_s=gap_s)`) and only *then* checks for open instants. But `cluster_events` (`src/va/roles/motion_source.py:39,52-53`) merges by extending `end_epoch` and **keeps only the first event's kind/attributes**. The lnr adapter emits `{"open": True}` zero-length instants for episodes still open at the query horizon (`lnr_eventlog_inproc.py:246-249`). Concrete failing input: closed episode `[T+30, T+60]` followed by an open instant at `T+70` (motion re-triggered within `gap_s` — the chatty-log case clustering exists for). The merge yields `[T+30, T+70]` with the closed event's attributes: not `open`, not zero-length, and `end < horizon`, so `open_instant` is False and `unsettled` is False. The watcher ingests `[30,70]` as settled, then quiet-advances the watermark to the horizon (`deferred_start` is None). Next pass the episode has closed as `[T+70, T+200]`, fails the `start_epoch >= watermark` filter, and the entire motion event — precisely a long, interesting one — is silently never ingested. This is the round-1-critical failure class re-entering through the cluster merge; the existing tests dodge it because `test_settled_episode_after_deferred_does_not_leak_watermark` deliberately uses a 35 s gap so the open instant never merges. Safe path: derive the unsettled/deferred detection from the **raw events before clustering** (deferred_start = min start over raw events that are `open`, zero-length, or end ≥ horizon; exclude those raw events from the clustering input), rather than changing shared `cluster_events` semantics that WS4.b also consumes; add a ≤ gap_s merge-ordering test.

**2. Minor — `src/va/web/jobs.py:209` — a resumed-but-not-yet-rerun job keeps accruing resume attempts across restarts it wasn't guilty of.**

`_resume()` bumps `attempts` on every `running` row but leaves the row in `running` state; it only gets rewritten when `_process` actually starts it. If the server restarts again before the resumed job reaches the front of the queue (e.g. systemd flapping on an unrelated startup failure after the lifespan runs), each flap bumps the same row, and after 3 flaps a perfectly recoverable job is terminally failed. Safe path: after bumping, knock the row back to `queued` (like `requeue_if_running`) — a genuine poison job re-marks itself `running` in `_process` before it crashes, so detection is preserved while restarts-before-rerun stop accruing guilt. Minor because the misfire is visible ("gave up after 3 resume attempts") and resubmittable.

**3. Minor — `src/va/pipeline/watch.py:284` — the watcher's `gap_s=30.0` and `open_instant_max_age_s=600.0` are function-default knobs that neither follow the profile nor appear in any doc/CLI.**

The security footage profile exposes a tunable `gap_s` on the motion-episodes scene-detector spec; a user who tunes it there still gets 30 s episode clustering for the watcher's chunk boundaries, silently. Hardcoded structure knobs are allowed, but the divergence from the profile's same-named knob is a surprise, and neither knob is documented in CLAUDE.md or COORDINATION.md (the CLI flags are documented; these two aren't reachable from the CLI at all). Safe path: read `gap_s` from the overlaid config's scene_detector spec, or document both knobs and why the watcher deliberately owns separate defaults.

Everything else I probed dissolved on inspection: the plain `ingest(uri, workdir=workdir)` call does apply the security profile (source-derived default in `_ingest_impl`), the shard-deletion/appearance-ref-reset block is correctly placed before the streaming pass and covered by a regression test, schema v6→v8 migrations are ordered and idempotent for both fresh and existing DBs, the monotonic watermark SQL protects the display-vs-DB paths, and the WS6.a/WS6.b "Done when" oracles (kill-mid-job exactly-once; exact-gap outage backfill; ~6-day SLA documented) are all present.
