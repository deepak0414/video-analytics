## Review: `origin/main..HEAD` (3 commits — review lifecycle, WT.4 part 2 + WT.10)

The lifecycle mechanics (forced declaration, trigger-vs-gate split, fail-closed verdict parsing, sentinel consumption) are implemented carefully and the sandbox tests genuinely exercise the real hook scripts with a fake reviewer. I verified several suspicions that dissolved: `.commit-approved` **is** gitignored in the committed `.gitignore` (so the sentinel doesn't perturb the scope hash and the test sandbox's gitignore matches reality); binary-file changes do alter the hash via the diff's `index` blob line; the `set -e` + `&& exit 0` pattern in commit-msg is safe; and the regex JSON-block extraction handles nested braces because the close-brace must be adjacent to the fence.

One major finding survived, and it contradicts the plan's own safety claim:

**1. major — `.githooks/post-commit:21` (also `pre-push:23,28`): the approval hash covers more content than the reviewer actually reviewed, letting uncommitted edits ship unreviewed.** The reviewer is invoked on the *commit range* (`origin/main..HEAD` at post-commit, `$remote_sha..$local_sha` at pre-push), but `review_scope_hash.sh` hashes the *working tree* vs origin/main (uncommitted tracked modifications + untracked files included). Scenario: the worktree has uncommitted modifications to a tracked file (exactly the current state of this repo — `src/va/registry.py`, `schema.py`, `test_trace_link.py` were dirty when 34294d3's review ran). The agent commits chunk A with `need_agent_review`; the reviewer sees only the commit range and approves; post-commit stores a hash that *includes* the never-reviewed dirty edits. The agent finalizes A, then commits the dirty edits verbatim as `wip:` — since `git diff origin/main` compares origin/main to the working tree, committing worktree-identical content leaves the hash unchanged — and pushes. Gate 2 prints "content already approved … skipping re-review", Gate 3 sees no provisional subject, and the wip content reaches origin having never been reviewed. This directly falsifies the plan's design note ("Uncommitted leftovers at commit time make the hash differ from the committed content, which fails safe", workflow-trust-plan.md:474-476), matrix row 21's "never avoids it", and the CLAUDE.md promise added in this diff ("it can never reach main unreviewed"). Fix direction: refuse to write `.git/.review-approved` when the worktree is dirty beyond HEAD (excluding `reviews/`), or review the `--worktree` scope from the hooks so review scope and hash scope coincide.

Three minor findings:

**2. minor — `.githooks/pre-push:22,34` and `post-commit:18`: fail-open when the range doesn't resolve.** `git diff`/`git log` errors are suppressed (`2>/dev/null`), and empty output is interpreted as "docs-only" / "no provisional subjects". The pre-push `$remote_sha` is reported by the server and may not exist locally (stale clone that hasn't fetched, then force-push — plausible given COORDINATION.md's multi-agent, multi-session premise); in that case Gate 2 and Gate 3 both silently skip. The design elsewhere is explicitly fail-closed; an unresolvable range should block, not exempt.

**3. minor — WT.4 "Done when" item (f) is only half-satisfiable, and the hooks' messaging overstates current enforcement.** Item (f) requires that an in-session `AGENT_REVIEW=skip` be "blocked by `bash_guard.py`", and `commit-msg:43-44` / `agent-review.sh:26` assert agents are "guard-blocked" from the sentinel/waiver — but no `.claude/hooks/` guard exists yet (WT.3 is sequenced later in the rollout). Until WT.3 lands, "human-only" is convention, not mechanism; the ledger digest presented to the human is the only thing standing between an agent and self-approval.

**4. minor — `.claude/agents/code-reviewer.md:1-4`: the interactive reviewer subagent claims "read-only, never modify anything" but has no `tools:` frontmatter restriction** (it resolves to "All tools", including Edit/Write/Bash), unlike the enforced headless path which pins `--allowedTools`. The plan's deliverable describes the reviewer as read-only; the convenience path relies on prompt-level restraint only.
