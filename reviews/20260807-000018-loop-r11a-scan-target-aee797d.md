## Full review

Review complete. I read the full diff, the deep-scan/ask/rule-planner sources, the configuration layer, the footage profile yamls across all four config dirs, the golden-ask fixtures, and the R11.a plan item. The core of the change is sound: `DEFAULT_TARGET` is gone from code, the profile gate resolves the recorded profile via `config_for` (record==reality, consistent with stale/reprocess), all shipped config dirs already carry `deep_scan: "off"` in security.yaml, a missing profile yaml fails closed (exception → "deep-scan failed" note, sweep skipped), and COORDINATION.md/CLAUDE.md were updated in the same change. Three findings survived verification.

**1. Major — the derive_scan_target degrade stage can only ever emit counting-noise words as the "subject" (`src/va/adapters/reasoner/rule_inproc.py:68`).** Stage 2 filters by `_STOP`, but stage 2 only runs when stage 1 (filter by `_SCAN_NOISE = _STOP ∪ counting-words`) emptied — so every word stage 2 keeps is by construction in `_SCAN_NOISE \ _STOP`, i.e. exactly the words stage 1 classified as *describing the counting, not the subject*. Worse, real subject nouns `color`/`colour`/`number` sit in `_STOP` and are dropped by both stages. Concrete input: the repo's own canonical query "how many times does the color change in the video?" derives `"the times change video"` — the micro-prompt becomes "name the times change video, including its color…". The offline e2e test passes only because the color-stub captioner ignores the prompt; on any real-captioner path that reaches the derivation (the rule floor, the documented qwen weak-planner malformed-params backfill at `ask.py:218`, self-escalation), a real VLM sweeps ~120 frames on a nonsense prompt and the arbitrary counts are prepended as the authoritative CODE-COUNTED line. This contradicts the change's own contract ("no derivable query subject = no sweep") — a noise-only string is not a derived subject. Safe path: when stage 1 empties, return `None` (honest skip), or keep subject-nouns like color/colour/number out of the drop set so "the color" survives; adjust `test_derive_scan_target_is_query_content_only` (which currently pins the noise-word behavior via `t2 is not None`) intentionally.

**2. Minor — the skip note conflates three distinct causes, and the new gate test can't distinguish them (`src/va/pipeline/ask.py:80` / `tests/test_deep_scan.py:405`).** `run_deep_scan` knows exactly why it returned `None` (it logs per-cause), but callers get one note naming all three possibilities. Consequences: the reasoner and the user are told the profile "may have" gated a scan even when the real cause was a missing video or target; and `test_security_profile_gates_deep_scan_off` asserts `"skipped" and "profile"` on a note that contains the word "profile" for *every* skip cause — a regression that broke `config_for` resolution while something else skipped the sweep would stay green. Safe path: surface the cause (a reason string on the return, or per-cause notes) and assert the profile-specific cause in the test.

**3. Minor — plan conformance: no evidence the second "Done when" ran (`architecture-evolution-loop.md:191`).** R11.a requires "A-EV golden-ask harness still green"; that harness is gated (`RUN_GOLDEN=1` + a real-model workdir) and nothing in the branch records a run. Static reading suggests it should stay green — the two golden ask questions ("the girl … dress …" → "the girl dress"; the birds/feeder query) derive the same targets as before, so cache keys are stable — but the done-when asks for the run, not an argument. Safe path: run the gated golden-ask harness and carry the result in the /task-commit digest.
