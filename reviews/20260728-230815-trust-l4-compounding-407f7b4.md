## Findings

**1. MAJOR — the herestring exclusion is dead code, so `<<< word` is misparsed as a heredoc opener and everything after it escapes the loop guard** (`.claude/hooks/bash_guard.py:375`). The check `line[cand.start():cand.start()+3] == "<<<"` can never be true: for input `<<< word`, the regex cannot match starting at the first `<` (the third `<` fails `-?\s*(["']?)[A-Za-z_]`), so the match always begins at the *second* `<`, and the sliced 3 chars are `"<< "`, never `"<<<"`. The third `<` sits *before* the match start, which the check never inspects. Verified against HEAD: `grep -q x <<< word` followed by `until ! pgrep -f job.py; do sleep 5; done` is **allowed** (the loop line is stripped as phantom heredoc body awaiting terminator `word`), while the shipped `<<< "$data"` fixture blocks only because `$` fails the name pattern — the exclusion contributes nothing. The attached form `<<<word` escapes identically. This means validation-matrix row 123 ("a herestring (`<<<`) … not mistaken for a heredoc") asserts a guarantee the code does not provide — the project's own tracked meta-defect, in the very commit whose plan notes catalogue its fourth occurrence — and the round-7 fix this code was written to deliver does not fix the reported case.

**2. minor — the `bash -c` payload scan does not stop at newlines, so a later *line's* `-c` payload is attributed to bash and false-blocked** (`.claude/hooks/bash_guard.py:466`). The break condition at line 471 lists `"\n"` as a separator, but `_flat` is built without appending newline tokens (unlike `_stream` at line 401, which was fixed for exactly this in round 5), so that branch is dead at line boundaries. Verified: `bash script.sh` + newline + `other -c 'until ! pgrep -f job.py; do sleep 5; done'` is **blocked**, while the shipped semicolon-separated fixture is allowed. Row 124 ("the payload scan stops at command separators") is contradicted for the newline spelling — the same missing-`"\n"`-token shape as the round-5 major, reintroduced in the second scan.

**3. minor — naive quote-parity on the heredoc-opener line rejects a real opener when an apostrophe appears inside double quotes earlier on the line, false-blocking heredoc authoring** (`.claude/hooks/bash_guard.py:378`). `before.count("'") % 2` counts an apostrophe inside a double-quoted string as an open single quote, so the genuine `<<'EOF'` opener is skipped, the body is tokenized as commands, and a loop being *written to a file* is blocked. Verified: `echo "let's go" && cat > w.sh <<'EOF'` + loop body + `EOF` is **blocked**, while the same command without the apostrophe is allowed. This is the round-6 "would have hit daily" false-block class (heredoc = data), resurfacing through round 7's own fix — conditional on an apostrophe, hence minor rather than major.
