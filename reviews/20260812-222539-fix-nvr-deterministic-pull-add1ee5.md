## Review: `origin/main..HEAD` (add1ee5, deterministic NVR pull)

The change replaces the dHash verify-and-trim + ReferenceLibrary design with a padded fetch ([start−10 s, end+2 s]) and a fixed-offset PTS cut, gated by a decode-based duration sanity check. The rewrite itself is clean: the retry loop fails closed, the atomic rename is preserved, deleted code took its tests with it and the new flow is pinned by new tests (padded bounds, cut offsets, retry/fail-closed, real-clip probe), the `_pull_window` signature change is logged in COORDINATION.md, and the empirical claims are reported with real ground-truth numbers rather than determinism-as-correctness. Checks that dissolved on inspection: the `_probe_cut` regex fallbacks are sound for `-f null` decode output; missing tail pad is harmless (the cut needs footage only up to `end`); the double retry nesting (outer×inner up to 16 fetches) is wasteful but correct.

**The finding — pre-pad availability is assumed, and the assumption fails exactly in the outage-backfill scenario the watcher documents.** The cut offset is the constant `PAD_PRE` (`nvr.py:277`), which is only correct when the device actually serves footage from `start−10 s`. At the ring edge — the documented "outage → watcher pulls what remains" recovery case — the pre-pad predates the oldest surviving footage even though `[start, end]` itself still exists. Whatever the firmware does there is bad: if it returns an error/no data, the pull raises; if it serves from first-available footage, the stream is short at the head, so a shortfall > ~4 s fails the ±2 s duration gate on every attempt (permanent fail-closed for recoverable footage the old exact-window fetch handled fine), while a shortfall of ~2–4 s *passes* the gate with the cut silently shifted late by that much — beyond the documented ~1 s timeline caveat, corrupting `start_epoch`-based motion-episode alignment. And a persistently failing pull is not benign in the watch loop: `watch.py:222-238` holds the watermark and aborts that camera's pass on ingest failure, so the camera wedges behind the dead window while the ring keeps expiring the episodes queued behind it — materially the same wedge interaction this commit's CLAUDE.md edit deletes and whose COORDINATION.md entry declares "gone with the refusal path." Safe path: on persistent duration-gate failure, fall back to one exact-window fetch with `PAD_PRE=0` and a 0-offset cut (the configuration whose single-request purity measured 1.000 over 300+ pulls), or detect the head shortfall (fetched padded duration vs. requested) and adjust the cut offset; and restore a documentation note that a persistently failing window still wedges its camera's watermark rather than claiming the interaction is gone.

I'm not reporting the 0-based `attempt` in the retry log line, the loss of accumulated cut-failure context when a mid-sequence fetch returns `None`, or the near-dead `Duration:` fallback in `_probe_cut` — all real but sub-minor. The commit subject is a provisional `need_agent_review:` and exempt from the clarity rule.
