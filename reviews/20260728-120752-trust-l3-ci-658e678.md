## Findings

**1. Major — `.github/workflows/offline-tests.yml:24` — `cache: pip` with no requirements file fails the workflow before pip ever runs.**
`actions/setup-python`'s pip cache resolver defaults to globbing for `requirements*.txt` / `Pipfile.lock`; this repo has neither anywhere (verified — dependencies live only in `pyproject.toml`, which is not in the default search set). When no dependency file matches, setup-python errors out ("No file matched to [**/requirements.txt or **/pipfile.lock]") and the step fails. Failure scenario: the first PR after merge shows `offline-tests` red on every run regardless of test health — the "un-bypassable gate" can never go green, WT.5's "Done when" ("a green PR shows the check passing") is unsatisfiable, and the check either blocks all merges or gets removed from required checks in frustration. Fix is one line: `cache-dependency-path: pyproject.toml` (or drop `cache:`). The WT.5 as-built note claims a "CI-readiness audit before the first run" but this was missed; the workflow has never actually run.

**2. Major — `.claude/hooks/bash_guard.py:332` — the `gh api` block is substring matching on route text and misses two working label-application routes, so the WT.7 label gate is still agent-servable.**
The rule blocks only tokens containing `/labels`, `/reviews`, or `/merge`. Statically certain bypasses: (a) `gh api -X PATCH repos/o/r/issues/9 -f 'labels[]=human-reviewed'` — the REST *update-issue* endpoint accepts a `labels` body field, and neither the route (`repos/o/r/issues/9`) nor the field token (`labels[]=…`, no slash) matches; (b) `gh api graphql` with an `addLabelsToLabelable` (or `addPullRequestReview`/`mergePullRequest`) mutation — no matched substring at all. This is the exact hole class the tip commit's own backstop rated major (matrix row 81), and for this gate CI is *not* the fallback layer — the `critical-paths` check trusts the label, so the guard is the sole enforcement of "the label is PROOF a human read the diff." COORDINATION.md's new entry ("agents are guard-blocked from applying it via … the REST API") overstates what ships.

**3. Major — `.claude/hooks/bash_guard.py:318-319` — noun/action are read at fixed positions `gargs[0]`/`gargs[1]`, so an interspersed flag defeats every `gh` rule.**
`gh issue -R owner/repo edit 9 --add-label human-reviewed` (and `gh pr -R owner/repo merge 14`) parse as `noun="-R"`, matching neither the label rule nor the merge rule; gh/cobra accepts persistent flags (`-R/--repo` is registered on the `issue`/`pr` command groups) between the noun and the action. I could not execute `gh` to demonstrate the ordering in this session, so this one is PLAUSIBLE rather than machine-verified — but the module's own design header records that position-matched parsing is precisely how earlier rounds leaked (`git_subcommand()` skips flags for exactly this reason; the gh rule doesn't). Failure scenario: same as finding 2 — self-applied `human-reviewed`, green critical-path check, no human ever read the diff.

**4. Minor — `tests/test_trust_guards.py:190` — the new guard rules (matrix rows 81) ship with zero test coverage.**
`BLOCKED_COMMANDS` still contains only `gh pr` spellings; none of the newly-blocked forms (`gh issue edit N --add-label human-reviewed`, `gh api repos/…/issues/N/labels`) were added, although the validation matrix "is the rollout's Done when" and the sibling rows 78/82/83 from the same commit each got tests. Failure scenario: a future guard refactor regresses the `gh issue`/`gh api` blocks and the suite stays green — the identical silent-regression path that let the original `gh pr`-only hole survive three trust PRs.

Suspicions chased that dissolved (not reported): the `CpRepo.__truediv__` staticmethod fixture is correct (special-method lookup binds via the descriptor, so the lambda gets one arg); the `golden` marker is registered in `pyproject.toml` so `-m "not golden"` won't warn; the heredoc expansion of `$changed` is single-pass (no re-expansion of filename contents); stale `base.sha` on late `labeled` events can only fail *closed* (extra files in the three-dot diff), never open; the space-join label ambiguity is unexploitable because applying any label token containing a review-label substring is blocked on the `edit` path.
