**Two new minors, both non-happy-path:**

1. **`enabled` is never validated as a boolean** (`src/va/configuration.py:68`). The overlay loader only checks `spec.get("enabled") is False` for the core-role guard; nothing rejects a non-bool value, and the two consumers disagree on one. With `enabled: "false"` (quoted string — a classic YAML accident), ingest's `_enabled()` sees a truthy string so the role **runs and is provenance-stamped**, while stale's `cfg.role(r).enabled` pydantic-coerces `"false"` → `False` and excludes the role from staleness **forever** — a running, stamped role that never reads stale after a model change is a missed stale, the one direction §6-b forbids. With `enabled:` (empty value, a half-drafted profile — the same shape `test_empty_role_body_is_tolerated` deliberately tolerates for role bodies), ingest silently disables the role while stale's `RoleConfig` raises `ValidationError` (verified against this venv's pydantic), which the per-video catch turns into "skip this video with a warning" — every video under that profile vanishes from the stale report. Safe path: in `_load_footage_overlay`'s existing per-role validation loop, reject a present non-bool `enabled` with a `ValueError` naming the file, matching the hardening standard this branch applied to every adjacent shape.

2. **Editing a profile to disable a role strands that role's existing rows, invisibly** (`src/va/pipeline/stale.py:56`). The `disabled` exclusion is computed purely from the current yaml — it doesn't distinguish a role that was *never run* (deliberately unstamped) from one that **ran, is stamped, and has live rows** from before the profile edit. If `security.yaml` later gains `ocr: {enabled: false}`, already-done security videos keep serving their OCR rows through search and the text index forever: stale won't flag them, no purge runs until a manual `va reingest`, and nothing tells the operator the data contradicts the profile's intent. Safe path: exclude a disabled role only when it is also *unstamped* (a stamped-and-disabled role is exactly "rows exist that the profile says shouldn't" — surface it), or document in CLAUDE.md that disabling a role in an existing profile requires reingesting its videos.

Commit subjects are all provisional `need_agent_review:` and exempt from the clarity rule; no silently-hardcoded content (the security vocab lives in the profile yaml, cited to plan §3.2, which is where domain content belongs); no contract breaks.
