## Full review

Review complete. Both findings from the prior review round (faf1310) are genuinely fixed in HEAD — `reingest_video` now carries the recorded profile forward with a `--profile` override and a test, and the dedup path validates the profile and prints a not-applied notice. The migration follows the repo recipe exactly (idempotent `add_column`, version-count assert, fresh + in-place-migrate tests), docs and COORDINATION.md were updated in the same change, and the `test_provenance_ingest` double was extended, not weakened. WS2.a/WS2.b "Done when" items each map to a test.

Two new findings survived verification:

**1. major — `src/va/pipeline/ingest.py:135` — the recorded `videos.profile` ignores roles.yaml `active_footage_profile`, while the roles actually run under it.** The recorded value is `profile or default_footage_profile(source_type)` — always "generic" today when no flag is given. But every registry `get_*()` calls `load_config()` with no argument (`registry.py:28` etc.), which resolves `footage_profile or roles_doc.get("active_footage_profile") or "generic"` (`configuration.py:118`) and merges that overlay into the role specs — including `get_ingest_classes`/`get_ingest_actions` vocab. So with `active_footage_profile: security` in roles.yaml (a selection mechanism documented in CLAUDE.md by this same branch), a plain `va ingest cam.mp4` runs every role under the security overlay yet records `profile='generic'` — the WS2.b deliverable (a durable record of the ingest domain) is silently wrong, and the dedup notice compares against the wrong value too. This is live WS2.a behavior, not a WS2.c-future concern. Safe path: make the recorded default follow the same precedence the runtime uses — e.g. explicit flag > roles.yaml `active_footage_profile` > source-derived default (the validation probe already returns the resolved name: `load_config(footage_profile=profile).footage_profile`) — or, if per-ingest and roles.yaml selection are intentionally independent axes, record that decision in COORDINATION.md and make the runtime path ignore `active_footage_profile` during ingest so record and reality can't diverge. Either way, add a test for the `active_footage_profile`-set combination — currently only the flag/no-flag combinations are covered.

**2. minor — `src/va/pipeline/manage.py:97` — `reingest_video` destroys the video's index before the footage profile is validated.** `remove_video` deletes the catalog row, all role rows, and the vector shard; only then does `ingest()` run the `load_config` probe. A typo'd `va reingest <vid> --profile secruity`, or a carry-forward whose recorded profile's yaml was since renamed/deleted, therefore raises `FileNotFoundError` *after* the removal — the video is left un-ingested and its recorded profile row is gone (media is kept, so this is recoverable by re-ingesting, but the fresh `va ingest --profile <typo>` path deliberately fails before any work, and reingest should give the same guarantee). Safe path: probe the target profile before calling `remove_video` — validate an explicit `profile` immediately, and for the carry-forward case look the video up first (its row is readable before removal) and validate `profile or video.profile` before anything is deleted; add a test asserting a bad profile leaves the reingested video's data intact.

Not reported after verification: the unknown-profile-on-new-video path leaving a row in its initial (non-failed) status is deliberate and test-asserted; provenance fingerprinting the base config is a reasoned, logged decision; the WS2.a top-level-`roles:`-shape minor is recorded as a WS2.c carry-over in the loop file; both commit subjects are provisional `need_agent_review:` and exempt from the clarity rule.
