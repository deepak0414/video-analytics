But I found a fresh bypass of the same `--no-verify` invariant that survived all prior rounds and isn't in the test tables.

**Primary finding (major).** The `commit -n` rule in `bash_guard.py:57` misses `-n` whenever git's `-m <value>` (or `-F <file>`) puts a non-flag token ahead of it. Verified against the actual committed guard:

```
exit=2  git commit -nm x            (control — blocked)
exit=0  git commit -m x -n          ← ALLOWED
exit=0  git commit -m msg -n        ← ALLOWED
exit=0  git commit -F /tmp/m -n     ← ALLOWED
```

`-n` is `--no-verify`. The rule's lazy flag-run `(?:\s+(?:--flag|-short))*?` can only consume *flag* tokens, so the message value (`x`, `'wip:`, `x'`, a filename) breaks the chain before the regex reaches `-n`. The rule's own comment claims it catches "any n-flag ANYWHERE in the flag run," and the literal `git commit -m x --no-verify` form *is* blocked — so the shorthand escaping is an oversight, not intentional scoping. `git commit -m "wip: x" -n` is the most natural way to type a no-verify commit, and it skips `.githooks/pre-commit` entirely (main-branch guard, secret scan, test-deletion guard, ledger append-only check). Major rather than critical only because the pre-push hook + post-commit review remain as backstops — the same calibration prior rounds used for the identical `-n` class.

The fix mirrors what already works for force-push: tokenize the segment and check for any `-*n*` short flag among `commit`'s flag tokens, instead of the position-sensitive regex.

**Secondary (minor, same root cause).** `tests/test_trust_guards.py:441` — every `-n` case in `BLOCKED_COMMANDS` places `-n` before the message or after flags only; none has a value token between `-m` and `-n`. So the suite stays green over this hole, again mirroring regex shape rather than the invariant the plan claims was made variant-based.
