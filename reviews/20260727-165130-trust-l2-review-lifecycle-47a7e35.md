Several new suspicions dissolved on verification: the `set -e` + `&& exit 0` idiom in commit-msg is safe (failures before the final `&&` are exempt); `git commit --amend -a` sneaks are caught because `-a` stages before hooks run; the empty-hash constant from a missing `origin/main` can never be blessed because both blessing sites verify the ref first; pathspec `reviews/*.md` matches across slashes so subdirectory smuggles are still covered; and `.commit-approved` is gitignored at HEAD so the sentinel never perturbs anything.

Three findings survived:

**1. major — `.githooks/pre-push:38` (root cause `scripts/agent-review.sh:76`): the headless reviewer consumes the hook's stdin, so in a multi-ref push every ref after the first backstop review skips all three gates.** The `while read -r local_ref …` loop reads the ref list from the hook's stdin, and every command inside the loop inherits that same stdin. `claude -p` in print mode reads piped stdin to EOF (the documented `cat file | claude -p` pattern) — so the first time Gate 2 actually invokes a live review, claude swallows the remaining ref lines, the next `read` gets EOF, the loop ends, and the hook exits 0 while git pushes *all* refs. Scenario: `git push origin feature-a feature-b` (or a branch plus a tag via `--follow-tags`) where feature-a's backstop review approves — feature-b then ships with no test suite run, no review, and no Gate 3 provisional-subject check, in a design whose whole point is that this is mechanically impossible. The sandbox tests never push two refs in one command, and the fake `claude` never reads stdin, so nothing catches it. Fix: redirect stdin away on the loop-body commands (`scripts/agent-review.sh "$range" </dev/null`, and ideally the pytest call too).

**2. minor — `scripts/agent-review.sh:78-82` + `.githooks/post-commit:29`: stale `*.md.err` files break the documented finalize step.** A failed/timed-out review leaves `reviews/<ts>-….md.err` behind (only deleted on that run's success; the next attempt uses a new timestamped name, so it's orphaned forever, and `.gitignore` has no `*.err` entry). The finalize instruction printed by post-commit — `git add reviews/ && git commit --amend` — then stages the `.err`, which the new pre-commit ledgers-only gate rejects. This is reproduced in the repo right now: `reviews/20260727-165130-…-47a7e35.md.err` sits untracked from the errored review of this very HEAD, and the next successful lifecycle's finalize will be blocked until someone hand-deletes it. Fail-closed, but the happy path documented by the hooks fails. Fix: gitignore `reviews/*.err`, or have agent-review.sh sweep stale `.err` files, or instruct `git add reviews/*.md`.

**3. minor — the docs exemption treats instruction-bearing `.md` files as inert.** `CLAUDE.md` and `.claude/agents/code-reviewer.md` match the `\.(md|txt)$` docs classification everywhere, so an agent can rewrite the interactive reviewer's rubric or the CLAUDE.md lifecycle instructions, commit with a plain `docs:` subject, and push with zero review (post-commit skips, Gate 2's docs-only test skips). The mechanical hooks (`.githooks/`, `scripts/*.sh`) stay gated, but behavior-shaping "docs" ride the row-28 exemption unreviewed — a gap the plan's docs-are-exempt decision doesn't appear to have weighed.
