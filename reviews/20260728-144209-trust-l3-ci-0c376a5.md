## Review: `origin/main...0c376a5` (WT.5–WT.7 CI gates)

**Verdict: request_changes** — one major, three minor.

First, the prior ledgers' findings really are fixed, and I verified rather than assumed. Driving the shipped guard directly: `gh api -XPATCH …/issues/14 --input /tmp/p.json`, `gh api --method=PATCH …`, `gh api graphql -F query=@mutation.graphql`, `gh issue -R o/r edit 14 --add-label human-reviewed`, `sed -i … scripts/check_critical_paths.sh` and `echo x > scripts/critical_paths.txt` all now exit 2, while the read-only `gh pr list --label human-reviewed` / `gh pr view 14` exit 0. The rename and large-changeset regression tests are real now (the latter writes ~99 KB, past the 64 KB pipe buffer), and the branch-protection recipe lists all three contexts. `tests/test_trust_guards.py` is 218 green in 9s. The CI install set is also right: the only third-party imports across `tests/` are PIL, fastapi, numpy, pytest and yaml, all covered by core plus `[web,dev]`.

**Major — the label gate only guards `gh`, and the label is the whole trust anchor** (`.claude/hooks/bash_guard.py:342`). Every rule in section 4 is reached only when `command_name(seg)` is `gh`. Measured against the shipped guard: `curl -X POST -H 'Authorization: token …' https://api.github.com/repos/o/r/issues/14/labels -d …` exits 0, and `gh auth token` — which hands over the credential to do it — also exits 0. I confirmed `api.github.com:443` is reachable from the agent shell (bare TCP connect, nothing sent). So an agent applies its own `human-reviewed` label in two allowed commands and `critical-paths` goes green with nobody reading the diff.

I want to be fair to the design here: the plan states plainly that bash guards are hardening rather than proof, with CI as the un-bypassable layer. That argument doesn't rescue this one, because WT.7 inverts the relationship — CI *consumes* the label as its evidence that a human read the diff, so there is no layer above it to catch a forged one. That is also why the last three backstop rounds each rated a new label-applying spelling (row 81, 85, 86, 88) as major; `curl` is the same class and is the most obvious remaining client, not an exotic one. Concretely, `COORDINATION.md:253` tells the other agent as fact that agents are guard-blocked "via `gh pr`, `gh issue`, or the REST API" — the REST API half is false; only gh's `api` subcommand is gated.

**Minor — the evidence check passes on an empty block** (`.github/workflows/pr-gates.yml:20`). It requires the marker `EVIDENCE: offline suite` and the absence of `<paste:`, so a body containing the marker line with nothing under it is green. WT.6's "Done when" is that a PR whose body lacks a *filled* Evidence section fails. An agent that tidies the template by deleting the placeholder line without running the suite satisfies P4 on paper and produces no evidence. The same substring heuristic errs the other way too: a PR that legitimately quotes `<paste: …>` in its body (documenting the template, as this PR would) fails the check despite carrying real output. Matching something like `[0-9]+ (passed|failed)` inside the block would close both.

**Minor — the three-dot diff does not "ignore main's moves" as the comment claims** (`scripts/check_critical_paths.sh:17`, wired at `.github/workflows/pr-gates.yml:40`). `actions/checkout@v4` on `pull_request` checks out `refs/pull/N/merge`, whose base parent is the *current* main tip, and `github.event.pull_request.base.sha` is the base tip captured at event time. When `base.sha` lags, it remains an ancestor of the merge commit, so `merge-base(base, HEAD) == base` and `base...HEAD` includes commits other people merged to main. Failure scenario: a docs-only PR opened before someone else's `scripts/` change merges to main is told it touched `scripts/` and must carry `human-reviewed`. This fails closed, never open, so it is not a hole — but it trains the human to apply the label reflexively, which is precisely what P5's bounded review is trying to avoid. `git merge-base HEAD origin/<base-ref>` is the usual fix.

**Minor — the as-built CI-readiness claim overstates the trust tests' insulation** (`workflow-trust-plan.md:1590`). The note asserts that `test_trust_hooks.py` / `test_trust_guards.py` build their own repos and neutralize `GIT_CONFIG_GLOBAL/SYSTEM` so the CI checkout "cannot affect them." They neutralize git config, not the ambient environment: `TrustRepo.run` at `tests/test_trust_hooks.py:51` does `os.environ.copy()` wholesale, and `.githooks/post-commit:9` exits early on `VA_AGENT_REVIEW`, which `scripts/agent-review.sh:75` exports for every reviewer session. Running `.venv/bin/pytest -q` in this session gives **5 failed, 406 passed, 2 skipped**; re-running the same file with only that variable removed gives **29 passed**. CI itself is unaffected (the variable is absent there), but the suite this PR promotes to the load-bearing required check and to the `/verify` evidence artifact is not environment-independent, and any reviewer agent that runs it will report a false red. The sibling file already handles exactly this at `tests/test_trust_guards.py:432` with `env.pop("VA_AGENT_REVIEW", None)`; the same line in the `trust_repo` fixture would fix it.
