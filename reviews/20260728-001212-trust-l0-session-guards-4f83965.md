Confirmed — the existing ledger matches are all about the earlier regex era (`[^|;&\n]*`), not this shlex-based gap. This is a new, undisputed finding.

## Review of `origin/main..HEAD` (WT.3 session guards)

I focused on the shipped enforcement code (`bash_guard.py`, `path_guard.py`, `stop_gate.sh`, `pre-push`, `settings.json`) rather than the plan doc, and ran the guard suite (176 pass) plus ~25 adversarial probes against `bash_guard.py` in a clean project dir.

**One critical bypass found.** `segments()` tokenizes with `shlex(..., whitespace_split=True)`, and shlex treats a newline as ordinary whitespace — it is consumed as a delimiter and never emitted as a token. The operator check at line 63 (`all(ch in "|;&\n()")`) therefore never sees a bare `\n`, so a multi-line Bash command collapses into a **single** segment. Every rule keyed on the first command of a segment — `git_subcommand` (force-push-main, `--no-verify`), the `rm -rf` rule, the `gh pr merge` rule, and the write-verb rule (`touch`/`cp`/`mv`/`ln` into protected paths) — is silently skipped for anything on line 2+.

Empirically verified (clean dir, no override):

| command | result | expected |
|---|---|---|
| `echo hi⏎touch .commit-approved` | **ALLOW** | block (self-approval sentinel) |
| `echo hi⏎git push --force origin main` | **ALLOW** | block |
| `echo hi⏎rm -rf .git` | **ALLOW** | block |
| `echo hi⏎git commit --no-verify -m x` | **ALLOW** | block |
| `echo hi⏎gh pr merge 14` | **ALLOW** | block |
| `true⏎cp /tmp/x .githooks/pre-push` | **ALLOW** | block |

Multi-line Bash commands are routine (the agent runs them constantly), so this trips even without adversarial intent, and it directly defeats the guard's central purpose: an agent can create the human-only `.commit-approved` sentinel or force-push `main` by placing that command on any line after the first. The override-token rule (`AGENT_REVIEW=skip`) and redirect-target rule still fire because they scan all tokens position-independently — but the write-verb, git, gh, and rm rules do not. Note the guard's own test matrix (rows 55/57/62/65/66) claims these are blocked "in every argv position / git-native spelling," yet no test uses a newline, so the suite gives false assurance. Fix direction: split `command` on newlines before/inside `segments()` (newline is a `;`-equivalent separator), not only on the punctuation tokens shlex emits.

Two probes that looked suspicious but dissolved: `git commit --no-verify=1` is rejected by git itself (`rc=129, "option no-verify takes no value"`), so allowing it is harmless; and `gh pr edit --add-label ready` is over-*blocked* (fail-safe, out of scope).

Everything else in the diff checked out: `pre-push` main-deletion guard, the exit-code-based stop gate with content-hashed cache key, the path_guard basename/prefix protections, and the `settings.json` deny-list trim (force-push coverage moved into bash_guard — which is exactly where the newline hole now lives).
