### Findings

**1. minor — `tests/test_relevance_gate_profile.py:150`: the "degrades to the base gate" test never makes the catalog fail.**
`Catalog(...)` → `schema.connect()` does `p.parent.mkdir(parents=True, exist_ok=True)` + `apply_schema`, so a nonexistent workdir yields a *freshly created* empty DB and `get_many` returns `{}` — no exception. Probe output: `gates keys: [None] / workdir created: True / catalog.db created: True`. The assertions pass, but the `except` branch at `retrieval.py:188-191` (the thing the docstring says is the point) has zero coverage and would still pass if the whole `try/except` were deleted. This is the repo's own "a regression test that cannot reproduce the original failure is decoration" lesson. Safe path: make the catalog genuinely unreadable — write a non-DB byte string to `<workdir>/catalog.db`, or monkeypatch `Catalog.__init__`/`get_many` to raise — and assert the warn trace fires.

**2. minor — `src/va/pipeline/retrieval.py:201`: a per-video config failure yields a *fully permissive* gate, not the base gate the docstring promises.**
`gates_by_video`'s docstring says "Any lookup failure degrades to the base gate," but only the *catalog* failure does. A *config* failure is swallowed inside `get_relevance_gate` (`retrieval.py:147-148`), which then returns `RelevanceGate(-inf, -inf)` — both floors gone — with no trace. Probe against a config whose base is `(min_rerank=-3.0, min_cosine=0.10)`: `get_relevance_gate(profile="warehouse", source_type="local")` → `RelevanceGate(min_rerank=-inf, min_cosine=-inf)`. Failure scenario: query a workdir under `VA_CONFIG_DIR=run-siglip/config` holding videos whose recorded `profile` has no yaml in *that* dir (a profile added only to `run-claude/config`, or one since renamed) — those videos silently bypass both floors, so anti-correlated frames and sub `-3.0` captions enter the evidence a security answer is built on, i.e. the exact inversion SR.5 exists to prevent, while every other video stays gated. Not reachable with the four profiles shipped today (`generic`/`security` exist in all four config dirs), which is why this is minor. Safe path: resolve the per-domain config in `gates_by_video` with an explicit failure path (or give `get_relevance_gate` a `default=` fallback), fall back to `gates[None]`, and emit the same `level="warn"` trace the catalog path does.

**3. minor — `COORDINATION.md:593` (combination coverage): the A-EV real-model combination is neither re-run nor stated as unaffected.**
The diff changes gate resolution for *every* video in `run-siglip` / `run-claude` / `run-qwen3vl` — not only security-profile ones — but the recorded evidence covers only A-LSSRVF (`.va-nvr`, 22 clips, with ground truth ✓). CLAUDE.md names `RUN_GOLDEN=1 VA_CONFIG_DIR=run-claude/config GOLDEN_WORKDIR=.va-shots pytest -m golden` as the attestation for real-model retrieval changes, and the immediately preceding COORDINATION entry (R11.a) recorded exactly that. Here it is absent. I verified statically that A-EV is numerically unaffected (see dissolved list), so this is a missing statement rather than a suspected regression. Safe path: either record a golden run, or add one line to the COORDINATION entry saying A-EV is unaffected *because* `generic.yaml` is `roles: {}` and no config sets `active_footage_profile`, so `config_for(None, …)` ≡ `load_config()`.
