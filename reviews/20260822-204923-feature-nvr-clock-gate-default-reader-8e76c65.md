### MINOR 1 — "12 h forgives an AM/PM flip" is only true for one sign of the loadfile drift
`src/va/sources/nvr.py:156` (and the comment block above it; echoed in `ocr_clock.py` `_to_epoch` docstring and CLAUDE.md). A consistent AM↔PM misread yields an observed epoch exactly ±43200 s from the true one, and the gate tests `_skew > 43200`. The true clock is `start_epoch + t + drift` (loadfile drift, ~1 s typical, up to 56 s), so skew is `43200 ± |drift|`: whenever the drift has the same sign as the flip the whole head reads foreign by a few seconds over 12 h → `_head_trim` finds no aligned tail → **reject**; on a live pull phase 1 retries and phase 2 then OCRs the same overlay pixels, so the reject repeats and the window holds the camera's `va watch` watermark. Scenario: a camera whose overlay renders "PM" such that RapidOCR reads "AM" consistently, with t=0 lagging start_epoch by 2 s → skew 43202 s → all-foreign → pull fails; the comment promises the opposite. Safe path: either set the OCR-path tolerance strictly above 12 h + max legit drift (e.g. `12 h + 120 s` — still five days below the ~7-day foreign band, costs nothing real), or strike the "forgives an AM/PM flip" claim and leave it as a documented residual.

### MINOR 2 — the 1.5 s head window (the round-3 major fix) is not pinned by any test
`src/va/media/frames.py:95` / `tests/test_nvr_clock_gate.py:289`. No test exercises `head_clock_frames` (grep: zero references under `tests/`), and every reader-through-`_verify_and_trim` test uses `_FakeFrameOcr` returning the *same* text for every frame, so the frame→time mapping and span are invisible. A revert to `first_frames` (0.4 s) — the exact state round 3 flagged — would pass the suite green, and the documented "a ~1 s same-camera head is TRIMMED not REJECTED" behaviour would silently regress. Safe path: (a) a unit test that `head_clock_frames(clip, 1.5, 8)` returns `t[0] == 0` and `t[-1] ≈ 1.45` on a 20 fps synth clip; (b) an integration test with a fake OCR keyed on frame content (head gradient → 7-day-stale overlay, body gradient → aligned) over a clip with a 1.0 s head, asserting `_verify_and_trim` returns a trimmed clip with trim ≈ 1.05 s rather than raising.

### MINOR 3 — stale "0.4 s / `first_frames`" statements survive in the shipped docstrings
`src/va/sources/ocr_clock.py:13` ("`media/frames.first_frames`") and `scripts/validate_clock_gate_va24h.py:14-15,22-24` ("the true 8 frames the reader decodes (0.4 s at 20 fps)", "via `first_frames` … decodes 8 frames per clip"). The reader now spans ~1.5 s via `head_clock_frames`, and the script's `--real` mode calls the shipped reader so it *does* inspect 1.5 s — its own docstring says otherwise. Scenario: the next session reads the script header, believes `--real` inspects 0.4 s, and mis-reasons about the proxy-vs-real gap / the "long head" reject classification. Safe path: update both docstrings to `head_clock_frames` / `CLOCK_HEAD_SECONDS` (~1.5 s, 8 sparse samples).
