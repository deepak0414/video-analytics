## Findings

**1. Major — `va reingest` of an epoch-placed chunk silently loses motion segmentation.** `reingest_video` (src/va/pipeline/manage.py:143-148) reattaches `camera_id`/`start_epoch` only *after* `ingest()` returns, but this diff (src/va/pipeline/ingest.py:246-260) makes Role 1 consume `start_epoch` *during* ingest. Remove → recreate leaves the row with a NULL `start_epoch` at Role-1 time, so the motion-episodes backend degrades to one full-span segment; the metadata is then reattached and provenance stamps the roles current, so `va stale` never flags the wrong segments. Since `va reingest` is the documented remedy for model changes *and* for a role that "reads stale," this is the exact path security-footage chunks will take. The existing reingest tests (tests/test_cameras.py:73,100) assert only that the metadata survives, not that Role 1 saw it. Smallest fix: in `reingest_video`, pre-create the row and attach the chunk metadata *before* calling `ingest()` (the pattern the new integration test already uses: `get_or_create` → `set_camera`/`set_start_epoch` → `ingest`), and add a reingest variant of the ingest oracle test.

**2. Minor — a misconfigured MotionSource is indistinguishable from a quiet chunk.** All four `security.yaml` profiles select `motion-episodes`, but every config dir's `motion_source` is still the sidecar stub with no `events_file`, which by design returns `[]` silently (src/va/adapters/motion_source/sidecar_inproc.py:30). Before this change that was harmless; now, for an epoch-placed chunk, "no events file configured" produces ZERO segments — the same output as a genuinely quiet chunk, with no warning anywhere. When WS4.c starts producing epoch-placed chunks under `run-siglip`, footage will land with no segments, no captions, and no actions, and nothing in the logs explains why. Safe path: have `SidecarMotionSource` (or the motion-episodes adapter) log a warning when it is queried with no `events_file` configured, or document in the profile/CLAUDE.md that `security` + real footage requires pairing with `motion_source: lnr-eventlog`.

**3. Minor — the real-footage combination changed behavior with only synthetic coverage.** Under `run-siglip`/`run-claude`/`run-qwen3vl` + `security` profile, every *existing* real NVR clip (all epoch-less local files, e.g. the 22 clips behind the `.va-nvr` golden workdir) now gets ONE full-span segment instead of pyscenedetect's per-shot segments — a per-clip captioning change on exactly the footage the NVR golden fixtures were calibrated against. The golden harness runs on a pre-ingested workdir, so it stays green while ingest behavior changed underneath it. Safe path: name this combination in the digest and either re-ingest + re-run the NVR golden set under the new profile, or state explicitly why the fixtures are unaffected (e.g. pyscenedetect already produced ~1 segment on static scenes — if verified, record that measurement).

Finding 1 is major, so the verdict is request_changes.
