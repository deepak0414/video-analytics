## Full review

I've verified each suspicion by running the guards directly. Findings below; all five majors were reproduced empirically, not inferred from reading.

**The pattern:** the guards are regex-matching the *exact command strings the tests contain*, and the test tables were written from the regexes rather than from the invariants. Every variant form I tried that a real agent would plausibly type got through.

**1. `git commit -nm "msg"` bypasses every commit-time gate** (`bash_guard.py:23`). The rule requires whitespace-delimited `\s-n\b`, so the clustered form doesn't match. I confirmed against real git in a scratch repo: `git commit -nm x` returned 0 and the `pre-commit` hook never ran. That single unblocked command defeats the branch guard, secret scan, test-deletion guard, and the commit-msg forced-declaration lifecycle at once — matrix row 9 holds only for the literal spelling in the test table.

**2. Gate machinery is writable from Bash** (`bash_guard.py:43`, `path_guard.py:92`). `path_guard` only runs on the `Edit|Write` matcher, and `bash_guard`'s write-verb rules cover `reviews/` and the three sentinels but nothing else. All of these were ALLOWed: `echo 'exit 0' > .githooks/pre-push`, `sed -i 's/exit 2/exit 0/' .claude/hooks/bash_guard.py`, `cp /tmp/evil.py .claude/hooks/bash_guard.py`, `chmod -x .githooks/pre-commit`. Because `setup-hooks.sh` points `core.hooksPath` at the working tree, an *uncommitted* one-line write disables L1 and L2 immediately — nothing needs to be committed or pushed. This defeats WT.3 goal (d) outright, and there is no layer behind it: `.github/` does not exist, so WT.5's CI and branch protection aren't there yet.

**3. The Stop gate's cache goes stale the moment you commit** (`stop_gate.sh:14`). The cache key hashes only `git diff HEAD` plus `git status --porcelain` — working-tree dirtiness, with no reference to the commit sha. Every clean tree therefore hashes identically (sha256 of empty input). Reproduced end to end:

```
1. clean tree, suite GREEN      -> rc=0   (caches the clean-tree hash)
2. dirty tree, suite RED        -> rc=2   "Cannot end turn: offline suite is red"
3. same RED code, now COMMITTED -> rc=0   (cache hit — pytest never runs)
```

Step 3 is not an evasion; it is the `wip:`/`checkpoint:` flow CLAUDE.md documents. Commit the broken code and the turn ends clean. The same staleness means a green run on one branch blesses a clean checkout of any other.

**4. Force-push to main is blocked in only one word order** (`bash_guard.py:25`). The pattern requires `--force` to precede `main`, so `git push --force origin main` blocks but `git push origin main --force` and `git push origin main -f` are allowed — arguably the more natural ordering. This is exactly the flag-reordering evasion (claude-code #40117) that the plan's own design note cites as the reason these regexes exist as "the enforcement layer" behind the advisory deny strings.

**5. Quoting defeats the human-only override tokens** (`bash_guard.py:29`, and identically 31/33/35). The rules match the literal `AGENT_REVIEW=skip`, so `AGENT_REVIEW="skip" git push` passes the guard; the shell strips the quotes and `agent-review.sh:28` sees `skip` and writes a WAIVED ledger. The agent can waive its own pre-push review — and `agent-review.sh:26` states the waiver becomes human-only "by mechanism once WT.3's session guards land," which is this PR.

Minor items: the test tables (`test_trust_guards.py:296`) enumerate only the orderings the regexes already match — no reordered flags, clustered flags, quoted override values, or Bash-mediated writes to gate machinery — and `test_stop_gate_green_then_cached:451` never commits, so it structurally cannot catch finding 3. Relatedly, the plan now marks rows 38–40 satisfied and describes rows 9–13/25 as demonstrated live, but rows 9, 10, and 11 hold only in their literal command form, so WT.3's "each L0 row demonstrated" isn't met in substance. Also, raising the reviewer timeout to 900 s (`agent-review.sh:79`) exceeds the 600 s Bash-tool ceiling on the *synchronous* pre-push backstop path — the plan's justification ("commits that trigger reviews run as background jobs") covers only the post-commit path, though this fails closed. And `.claude/settings.local.json` is newly gitignored but absent from `path_guard`'s PROTECTED list while its sibling `settings.json` is protected.

Nothing was deleted or weakened in the existing suite, and the round-5 carry from PR 2 (self-blessing `.git/.review-approved`, fabricated ledgers) is genuinely fixed. No prior ledger disputes any of the above.
