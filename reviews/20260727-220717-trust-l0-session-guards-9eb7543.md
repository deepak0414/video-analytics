## Review — `trust/l0-session-guards` (origin/main..HEAD, 2 commits)

**1. (major) `.claude/hooks/bash_guard.py:46` — git global-flag insertion (`git -c …`, `git -C …`) defeats both the clustered `-n` commit rule and the *entire* force-push block.** Empirically verified against the rule regexes: `git -c foo=bar commit -nm x`, `git -C . commit -n -m wip`, and `git -c color.ui=false push --force origin main` all come back **allow**. The `-n` rule anchors on `\bgit\s+commit\b` and the force-push logic is gated on `\bgit\s+push\b` (bash_guard.py:86), so any global flag between `git` and the subcommand skips them entirely. The asymmetry is clearly unintended: rule 1 (`\bgit\b[^|;&\n]*--no-verify`) *does* tolerate intervening flags, and the blocked-commands test table even includes `git -c foo=bar commit --no-verify` — but not the `-n` or push analogues. This falls squarely under the file's own "rules target INVARIANTS, not literal spellings" standard, by which the reorder and cluster variants were judged major in the prior rounds; and for force-push there is still no layer behind the guard (pre-push has no force detection, WT.5 CI/branch protection doesn't exist yet), so `git -c x=y push -f origin main` can rewrite remote main. Fix is one-line per anchor (e.g. `\bgit\b[^|;&\n]*\bcommit\b` / `\bgit\b[^|;&\n]*\bpush\b`), plus the matching table rows.

**2. (minor) `.claude/hooks/bash_guard.py:96` — `git push --force origin HEAD` from a main checkout evades the bare-force branch resolution.** Verified: `nonflags` is `["origin", "HEAD"]` (len 2), so the `len(nonflags) <= 1` heuristic never resolves the checked-out branch, `HEAD` contains no `main` token, and the command is allowed — yet with the default `push.default` it force-pushes the current branch (main) exactly like the bare `git push --force` the round-3 fix closed. Treating `HEAD`/`@` refspec tokens like the no-refspec case would close it.

**3. (minor) `.claude/hooks/stop_gate.sh:15` + `.claude/hooks/bash_guard.py` — the Stop gate's own green-cache is self-blessable.** `.git/.stop-gate-green` is not in any bash_guard rule or path_guard's `PROTECTED`, so the agent can compute the cache key and `echo <hash> > .git/.stop-gate-green` (or simply `mv .venv/bin/pytest` aside, hitting the `[ -x ] || exit 0` early-out) to end a turn on a red suite without running pytest. Inconsistent with the explicit protection given the analogous `.git/.review-approved` self-blessing vector (matrix row 38). Minor because the Stop gate is L0-only and already bounded by the harness's 8-consecutive-blocks override, but the two `.git/` sentinels deserve the same treatment.

**4. (minor) `.claude/hooks/stop_gate.sh:28` — the cache never persists in linked git worktrees.** In a worktree `.git` is a *file*, so `echo "$cur" > .git/.stop-gate-green` fails ("Not a directory"); with no `set -e` the script still exits 0, so behavior is correct but the full offline suite re-runs at every single Stop in worktree sessions (which this multi-agent setup plausibly uses). Use `git rev-parse --git-dir` for the state path.

**5. (minor) `.claude/hooks/bash_guard.py:90` — `\b(main|master)\b` matches hyphen-delimited branch-name substrings.** Verified: `git push -f origin feature/main-page` is blocked (word boundary before the `-`), so legitimate force-with-lease to any branch containing `main`/`master` as a hyphen/slash-delimited word is a false positive.

Non-findings, verified and dropped: `--amend` does not trip the `-n` cluster rule; `path_guard`'s `normpath` closes `../` traversal and absolute-path variants; `2>&1`-style redirects after a sentinel token don't false-positive (write verb must precede the path); the 93-test count claimed in the plan matches the actual parametrization; the COORDINATION.md shared-interface entry and CLAUDE.md sync are present; no existing tests were deleted or weakened; the reviewer-timeout raise (480→900s) is documented with its background-push caveat.
