### Findings

**1. minor — `COORDINATION.md:618` / test coverage: the A-LSSRVF attestation doesn't exercise the changed code path, and no fixture pins the result the change exists to produce.**
The relevance gate lives only in `retrieve()`. `test_golden_queries.py` calls the per-modality searches directly (`visual_query`, `search_captions`, `search_actions`, `query_objects`, …) and never `retrieve()`, and no `nvr0801_*.yaml` carries an `ask_questions:` block — only `birdfeeder_0413_1405.yaml` and `eiLeBJUf1iE.yaml` (both A-EV) do. So "A-LSSRVF … `-k nvr` = 17 passed / 8 xfailed, baseline-identical" is true but structurally incapable of detecting this diff; the A-EV line (which includes the 2 `ask` questions) is the only golden evidence that touches the gate. Failure scenario: someone later restores a single base gate, changes the profile-resolution order, or drops the `retriever:` override from `run-claude/config/profiles/footage/security.yaml` — the offline suite still passes (it builds its own config dir) and the nvr golden run still reports 17/8, so the 3-of-8-questions-emptied starvation returns undetected on real footage. Safe path: add an `ask_questions:` block to one or two nvr fixtures asserting the question yields evidence (no "no candidate cleared the floor" note) and run `test_golden_ask.py` against `.va-nvr`; or state in the COORDINATION entry that the nvr golden harness does not cover `retrieve()` and that the end-to-end 13/25 · 0/8 numbers rest solely on the ad-hoc measurement.

**2. minor — `config/roles.yaml:107`: the commented-out "To enable" recipe now re-creates the exact failure R11.b fixes.**
`config/profiles/footage/security.yaml` deliberately omits the `retriever:` override, and its new NB justifies this with "declaring it here would fail config load" — true only while `retriever` is commented out of `config/roles.yaml`. The moment a reader follows the enable recipe at `config/roles.yaml:107-109` (`min_rerank: -3.0` / `min_cosine: 0.05`), the role exists, the security overlay loads legally *without* a floor override, and every `--profile security` video in that workdir is judged by an A-EV-shaped absolute cosine floor — the starvation this commit measured at 3-of-8 questions emptied — while the NB explaining why the override is absent has silently become stale. Failure scenario: a user enables the stub-config gate as documented, then asks "was anyone at the door?" over NVR footage and gets "no candidate cleared the floor — no match" with the real events sitting in the ungated pool. Safe path: extend the recipe comment in `config/roles.yaml` to say that enabling `retriever:` also requires adding the `security` footage-profile override (with the measured 0.0), and note the conditional in the security.yaml NB.

**3. minor — `src/va/pipeline/retrieval.py:129`: `profile`/`source_type` are positional behind an unused `workdir`, so a positional call silently returns the wrong gate.**
`workdir` has never been read by this function; the two new parameters were appended after it. `get_relevance_gate("security", "local")` binds `workdir="security"`, `profile="local"`, `source_type=None`, which takes the `load_config()` branch and returns the **base** floors — no error, no trace, just the un-domain-calibrated gate. Every current call site uses keywords, so nothing is broken today; this is a trap for the next caller of a function COORDINATION.md now advertises as a shared interface. Safe path: make the new parameters keyword-only (`def get_relevance_gate(workdir=None, *, profile=None, source_type=None)`), which turns the mistake into a `TypeError`.
